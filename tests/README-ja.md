**5つのうち2つは否定的な主張であり、そこが要点である。** **フォールバックはフォールバックとして書かれている。これらの検査は「それを選ぶことが検査を1つ外すこと」を記録する。** **無ければ、その1つは静かに消える。**

## 同じ検査が、2つの時刻に

**制限は計画時（`admit.py`）に検査され、出て行く1フレームごとに（`backend/gate.py`）もう一度検査される。2つ目は1つ目の繰り返しではない。**

計画時は軌道全体を持ち、時計を持たない。門は1フレームと、**ループの中で実測された経過時間**を持つ。**2つ目にしか存在しないものが3つある**: **隣り合う2フレームの間隔**——ファームにソフトスタートが無い以上、これが指令を段差にするかどうかを決める——、**送る時刻**、そして**自由度がどのモーターへ行くか**。

⚠️ **そして2つは、効く向きに食い違いうる。** `admit` を通った軌道でも、**門のところで段差を作りうる**——**遅れた刻みが1つあると、送信が標本を飛ばすからである。** **その場合は `test_backend.py` が主張しており、隠さずに自らの限界を名乗っている**——下を見よ。

## `05 §2.2` が「書けない」と書いた検査

**設計ノートは、周期について検査できるのは2つだけだと挙げていた。どちらも形であって、性質ではない**——**「締切方式で書かれている」**と、**「`sleep(period)` を毎回呼んでいない」**。⛔ **そのどちらも書かれていなかった。書く対象のループが無かったからである。**

**`test_cycle.py` は、それを性質として書く。** ループは時計を呼ぶ側から受け取る——`engine/` は `time` を import できない——ので、**偽の時計がループを走らせ、眠るよう要求された量を数える。** 2つの形の検査は、こうなる: **すべての sleep が余計に眠っても、刻み `n` の締切は `start + n * period` である**ことと、**1回の sleep の要求が `period × sleep_fraction` を超えない**こと。

⚠️ **`grep` は、その行がソースに在ることは見える。走ったときにその行が成り立つことは見えない**——**毎回 `deadline - now` だけ眠るループは、`sleep(period)` という文字列を1つも含まないまま、それを書いたのとまったく同じに振る舞う。**

## 5つのうちに入らない検査

**`test_intent.py` は、境界を両側から押さえている。** **型の `quality` 欄は、スキーマが受け取り、コードが無視する**——**そして両方が主張されている。片側だけなら境界は崩れる。** **語彙が入る日、後半は消すのでなく書き換えられる。**

## なぜ決定論を静的に見るのか

**`test_purity.py` は `engine/` の全ファイルの import を読み、`random`・`time`・`os`・`socket`・LLM のクライアントのどれかがあれば落ちる。**

**同じ入力を2回走らせて比べても、証明にはならない。** **その2回が、たまたま一致しただけかもしれない。** **見るべきは import であり、AST はそれを、grep が docstring の中の語を見つける場所で見つける。**

## 直さずに記録している限界

**門がフレームを弾くと、最後に通した組を保つ——*送らない*は*止まる*ではないからである。ゆえに遅れた刻みが1つあるだけで軸が凍り、門の中にそれを戻す道は無い。**

理由は、門の基準が*最後に通した値*であるのに、送信が提案するのが*壁時計の値*だからである。**提案は先へ進み続けるので、開きは縮まらない。** **機体は保たれ——それが安全な向きである——そして端には着かない。それはこの機構の目的ではない。**

**`test_a_late_tick_freezes_the_axis_and_the_gate_does_not_recover` が、これを記録し、3つの選択肢を並べている。** 設計としてではなく**限界**として書いてある——**選ぶのは著者である**——そして、それが選ばれるまで振る舞いを主張しておく。**変えることが黙って起きないように。**
