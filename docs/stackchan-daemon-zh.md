# Stack-chan 的守护进程 — 启动与停止

✅ **循环、套接字和客户端都已经建好——2026-10-18。** `projects/stackchan/daemon/` 持有纯核心（`room.py`）和边缘（`__main__.py`），`projects/stackchan/hook/` 持有钩子运行的客户端，`tests/test_stackchan_daemon.py` 对前者持有二十六条主张，`tests/test_stackchan_hook_client.py` 对后者持有二十一条。✅ **而且同一天它被安装了**——launchd 用户代理在登录时启动守护进程，全部三十三个钩子事件都调用客户端。**安装是一台主机上的一个位置，不是仓库的性质**（见[安装的现况](#安装的现况)）。

⚠️ **它是为了什么。** Claude Code 的钩子是一个事件一个进程，而 `Focus` 与 `Companion` 是一个必须在事件之间存活的物体。守护进程就是那个物体，加上一个时钟和一个套接字。它是链条的中段——**钩子 → 守护进程 → 电线 → 固件**——也正是它，让机器人属于房间，而不是属于一个开着的终端。

✅ **它被安装在一台主机上，而仓库持有的是作业的副本，不是作业本身。** `projects/stackchan/launchd/embodied-kinetic-loom.stackchan.plist` 就是那个文件，用两个绝对路径点名这台主机；活的副本在 `~/Library/LaunchAgents/`。⛔ **仓库里的 plist 不是正在运行的守护进程**——安装是 `launchctl bootstrap`，卸载是它的反面。`tools/check_i18n.py` 只看三份副本是否一致，不看设计；**两个进程由 `tests/test_stackchan_daemon.py` 和 `tests/test_stackchan_hook_client.py` 看着，而安装没有任何东西看着。**

## 为什么状态住在主机上

⚠️ **另一个方案被考虑过: 把阶段、注视和定时器放进固件，让电线运送事件而不是身势。** 它没有被选中，理由记在这里，因为**省略不是中立的**。

⛔ **两个设计在电线上分叉。** 状态在主机上，电线运送**身势**；状态在固件里，电线运送**事件与窗口的名字**。**已经确定的电线运送身势**，0.19.0 的契约是照着它写的。⇒ **以后再把状态移过去，不是移植，而是协议变更。**

**设备侧的设计会买到什么:** 完全没有常驻进程——没有 launchd、没有套接字、没有锁; 跨 Mac 重启仍然存在的状态; 多个主机喂给同一个身体; 以及**在这个仓库不在磁盘上时仍能运行的振舞**。

**今天要付出的代价:** 自定义固件——这个工房最封闭的一步，恢复路径未经验证，NVS 的零点已经移动过一次; **同一套规则在 C++ 里的第二份实现**——这个仓库的试验到不了那里，而它把「把一列写两遍」称为缺陷; 每次改变振舞都要重新烧写; 以及跨过一条还不存在的电线来调试。

⚠️ **设备侧的设计常被以为能买到、其实买不到的东西:** 主机消失后仍继续工作的机器人。**死掉的守护进程已经不是失控的机器人**——什么都不持续流动，待机归固件所有。两种方案下，机器人都回到自己的振舞。状态放在主机上真正失去的东西更窄: **仓库必须在磁盘上**，以及**阶段不能跨守护进程重启存活**。

⚠️ **当以下任何一条成为要求时，这个决定会被重新打开:** 在这个仓库缺席时的振舞; 跨主机重启的状态; 多个主机喂给一个身体; 或者完全没有常驻进程。**今天，它们都不是要求。**

## 启动与停止，不是机器的启动与停止

⚠️ **固件的待机行为是它自己的。** 守护进程只添加决定，不拥有身体。⇒ **启动守护进程不会启动机器人，停止它也不会让机器人驻机。** 这一点之所以重要，是因为机器1的协议里没有停止命令，而机器2的协议在这里根本没有被确定。

⛔ **死掉的守护进程不是失控的机器人。** 这是身势命令设计的性质: 什么也不持续流动。固件最后被告知的，是一个身势，而它的开始与结束归固件所有。守护进程死掉时，没有任何东西继续到达。

## 生命周期

| 状态 | 由什么进入 | 什么是真的 |
|---|---|---|
| `stopped` | 登录前、`bootout` 后、正常退出后 | 没有套接字，没有状态 |
| `starting` | launchd，或手动运行 | 套接字已 bind；**什么都还没有发送** |
| `ready` | bind 成功 | 循环等待套接字与下一个期限 |
| `stopping` | `SIGTERM` 或 `SIGINT` | 不再接受新事件；关闭；退出码 0 |
| `stopped` | 退出 | 套接字被 unlink |

⚠️ **没有持久化。** 阶段、定时器、注视与失败计数，全部从 `present` 重新开始。**重启后的守护进程不会恢复**: 下一次迁移会重新立起阶段。代价要点名: 如果它在一轮对话的途中重启，机器人会显示 `present`，而那一轮仍在运行——直到下一次迁移。

⚠️ **启动不发送问候。** 第一个运动来自第一个事件，而不是来自守护进程活着。**「你好」是为机器而做的运动**——与 `working` 期间让身体保持不动是同一条规则。

## 谁启动它 — launchd，而不是钩子

✅ **macOS 的用户代理**（`LaunchAgents`），带 `RunAtLoad` 与 `KeepAlive`。三个理由:

- **登录时启动**: 使用者什么也不打开，而这正是把这一页放到这里的那个要求;
- **崩溃后重启**: 套接字的客户端做不到这一点;
- **只有一个所有者**: 生命周期住在一个地方，而不散落在钩子里。

⛔ **钩子不 spawn 守护进程。** 会 spawn 的钩子是没有记忆的监督者: 同时到达的两个事件会竞争，而从钩子启动的守护进程会继承那个钩子的环境。**钩子是传令兵，不是监督者。**

⚠️ **仅靠套接字激活不够**（尽管 launchd 可以做到）: 事件停止时机器人必须入睡，而**入睡需要一个活着的进程去注意到期限**。守护进程活着，并等待。

⚠️ **标签是 `embodied-kinetic-loom.stackchan`**——一个字符串，不是一个域名；不为它发明反向 DNS。作业以 `WorkingDirectory` 指向仓库根目录、用绝对路径的解释器运行，因为 launchd 启动作业时没有它自己的工作目录。

## 单一实例，与陈旧的套接字

⚠️ **套接字就是锁。** 它的路径是 `/tmp/ekl-stackchan-<uid>.sock`，在 bind 之后设为模式 `0600`——因为套接字文件会继承进程的 umask。短路径不是装饰: macOS 的 `sun_path` 是 104 字节，而 `/var/folders/…` 下的 `$TMPDIR`，在用户名较长时足以撞上这个上限而坏掉。

⚠️ **启动在 bind 之前先探测:** 先向路径 connect。如果 connect 成功，**另一个守护进程活着，而这个进程不对机器说一个字就退出。** 如果它以 `ECONNREFUSED` 或 `ENOENT` 失败，路径就是陈旧的——unlink 它，再 bind。

⛔ **没有 pidfile。** pidfile 会变陈旧，而且无法被探测；套接字可以回答。**一把锁，不是两把。**

## 钩子发送什么

**每个事件一行 JSON:**

```
{"session": "<session_id>", "event": "<hook_event_name>"}
```

⛔ **提示词不在消息里，而模式会拒绝它不认识的键。** 一个仅仅被忽略的字段可以搭车；一个被拒绝的字段不能。**隐私靠构造，不靠政策。**

⚠️ **客户端不发送时间。守护进程在行到达时自己盖一个时间戳**，用单调时钟。两个理由: 客户端是没有状态的传令兵，而会倒退的墙钟是层会拒绝的谎言。**`Decision` 里的时间是守护进程的，不是钩子的。**

⚠️ **客户端等待 100 ms，任何失败都以退出码 0 静默结束。** 钩子不得阻塞一轮对话，也不得把机器人变成错误。**错过的事件被丢弃，不进入队列**: 迟到的事件是关于它何时发生的谎言，下一个事件会修复阶段，待机时钟会修复其余部分。

⚠️ **代价要点名:** 如果 `SessionStart` 时守护进程不在，就没有问候，机器人显示 `present` 直到下一次迁移。如果 `SessionEnd` 时它不在，机器人就靠待机定时器入睡。两者都能在痕迹里看见，两者都不是错误。

✅ **客户端本身现在有了**——`projects/stackchan/hook/`，一个事件一个进程。它读标准输入（上限 1 MiB），**只重建 `session` 与 `event`**，所以提示词无法搭车，发送那一行，**不读回信**，什么也不打印，无论什么失败都以 0 退出。**守护进程不在，不是钩子的失败。** ✅ **自 2026-10-18 起它有了调用者：`~/.claude/settings.json` 的全部三十三个事件都运行它**（见[安装的现况](#安装的现况)）。

## 等待的循环

⚠️ **不轮询。** 守护进程在监听器上等待，超时等于下一个期限——`min(hold_until, idle_until, quiet_until)`——并在 `settled` 或 `slept` 决定该发出的那一刻醒来发出它。**这没有发明任何间隔**: 层里不添任何 tick 常量。

⚠️ **一次一个事件，按 accept 循环取到的顺序。** 没有队列，没有重排。未能在同样的 100 ms 内送达其行的连接会被关闭；**一个数，只在一个地方命名，两端共用。**

⚠️ **时钟是单调的。** CLI 里的台本时刻是另一个领域——台本给出的秒——而层的契约在两边相同: `offer(session, event, at)` 接收一个值，从不读时钟。

## 停止，以及身体会做什么

⛔ **收到 `SIGTERM` 时，守护进程停止发送。它不发送驻机、不发送安定、不发送最后的动作。** 没有可以安全发送的东西: 这台机器没有停止命令，而关机时发明的动作，是没有人选择过的那一个运动。

⚠️ **舵机被放任不管时，头可能垂下来**——SCS 舵机在待机时释放扭矩。**那是机器的待机行为，不是故障**，而且在手头的个体上看见过。

⚠️ **守护进程停止后，固件如何处理最后的脸，这里没有确定。** 如果固件保持它，脸就留着；如果固件自己的待机接管，它就会改变。⛔ **0.19.0 的契约也没有定它**——契约里的 `face: null` 是「不改变」，而对没有任何一行到达时板子做什么，它什么也不说。

## 机器是可选的

✅ **守护进程在没有机器的情况下运行**，而且最初就是这样做、这样试的。**今天一根电线也不打开**: 守护进程编码帧并把它写成一行（见下），而延迟打开的那条路是设计，尚未建起。

⛔ **机器的错误被记录并丢弃，永不致命。** 在 `KeepAlive` 之下，机器缺席加上致命错误就是崩溃循环——**监督者会一直杀死那个本该在等待的东西。**

## 写下帧，而不发送

✅ **自 0.19.1 起，每一个决定都经过 `projects/stackchan/outbound.py`**，当帧不是 `None` 时，守护进程把它写成一行:

```
{"frame": "{\"face\":null,\"gesture\":null,\"light\":\"breathe\"}", "sent": false, "at": 6497.584270416, "session": "…"}
```

- **帧在机体该显示的东西发生变化时写下**——脸或光——**或者选中了身势，或者它是这个进程的第一个决定。** ⛔ **第一个决定一定发出，因为在那之前的机体状态是未知的**; 脸由帧自身的状态补上，所以机体不必记住自己曾映着什么。
- ⛔ **事件的理由并不划分状态变化**，所以规则读的是状态，不是理由。`blocked` 中的 `PostToolUse` 以理由 `OBSERVED` 回到 `working`，光却可能不动; 担忧改变光，不改变阶段。
- ⚠️ **这不是流。** 在观测到的那次运行里，紧随第一个帧的 `PreToolUse` 没有写下第二行。
- **那一行属于编码器**——`engine/backend/protocol_stackchan.py`，与 `tests/test_stackchan_wire.py` 所守的是同一个——**所以日志不会偏离 `schemas/stackchan-command.schema.json`。**
- ⛔ **什么都不会离开进程。** 每一行的 `sent` 都是 `false`，对面没有传输路径、没有渲染器、没有 LED 驱动。**一行日志不是电线**，而 ⛔ **它也不是运动的记录**——那个要求写在 `CLAUDE.md` 里，形状仍然开着。

## 已决定的，与未决定的

**在这里决定的:**

- launchd 用户代理，`RunAtLoad` 与 `KeepAlive`；标签 `embodied-kinetic-loom.stackchan`;
- `/tmp/ekl-stackchan-<uid>.sock`，模式 `0600`，先探测再 bind，没有 pidfile;
- 由守护进程盖戳的单调时间；没有客户端时间;
- 一行 JSON，未知键被拒绝，提示词在结构上缺席;
- 客户端等待 100 ms，失败即丢弃，没有队列;
- 等待下一个期限；没有固定的 tick;
- 没有问候、没有驻机、没有持久化;
- 机器的联接是可选的，且永不致命。

**在这里未决定的:**

- ✅ **成帧已经定了（0.19.0），而这一页仍然不拥有它**——一行 ASCII JSON，`face` / `light` / `gesture`，在 `schemas/stackchan-command.schema.json` 里，由 `engine/backend/protocol_stackchan.py` 编码。✅ **自 0.19.1 起，守护进程调用那个编码器，并带着 `sent: false` 写下它本该送出的那一行。** ⛔ **未决定的是传输路径**: 那一行如何到达板子，由谁打开。**守护进程一根也不打开**，而 `projects/stackchan-firmware/`——只有源码，一次也没有被构建、没有被烧写——拒绝每一个身势;
- 固件在待机时与停止后做什么;
- 第二个身体——每台机器第二个守护进程——是否需要不同的东西。

## 安装的现况

**2026-10-18，在作者的 Mac（uid 501）上测量。** 这不是设计，而是做了什么、看到了什么的记录——也不是测试。

- **作业。** `~/Library/LaunchAgents/embodied-kinetic-loom.stackchan.plist` 被 bootstrap 进 `gui/501/embodied-kinetic-loom.stackchan`。`RunAtLoad` 与 `KeepAlive` 为真，解释器是绝对路径（`/opt/homebrew/bin/python3`），`WorkingDirectory` 是仓库根目录。**`projects/stackchan/launchd/` 里的副本是同一个文件。**
- **套接字。** `/tmp/ekl-stackchan-501.sock`，模式 `0600`，归用户所有。守护进程的第一行日志是 `{"daemon": "listening", …}`，在 `/tmp/ekl-stackchan-daemon.log`。
- **调用者。** `~/.claude/settings.json` 带有一个 `hooks` 键：三十三个事件名各自映射到一条命令——`cd "<仓库根目录>" && /opt/homebrew/bin/python3 -m projects.stackchan.hook`。⛔ **命令点名这台主机的路径**——与 plist 相同的限制。⚠️ **那个文件也持有用户的凭据，所以不复制到这里**；这一页记录的是形状，不是那个文件。
- **一个帧行，被看到了（2026-10-18，0.19.1 之后）。** 守护进程用 `launchctl kickstart -k` 重启到新代码上，一次真实的钩子事件到达，日志恰好增加了一个帧行——`face: null`、`light: breathe`——带着 `"sent": false`。**随后的 `PreToolUse` 没有写下第二个帧**，因为状态没有改变。⛔ **观测到的是一行日志，不是运动。**
- **一次端到端的运行，被看到了。** 一个嵌套的 `claude -p` 会话在守护进程的日志里留下五行: `SessionStart` → `greeting`; `UserPromptSubmit` → `working`，身体被一秒的地板压住; `MessageDisplay` → `observed`; `Stop` → `closing`; `SessionEnd` → `resting`，带 `settle`。**每一行都读到 `sent: false`。** ⚠️ **这就是整条链**——真实的钩子、一个事件一个进程、一个房间——**而它对机器人什么也没说**，因为没有电线。
- **停止。** `launchctl bootout gui/501/embodied-kinetic-loom.stackchan` 停止作业，套接字消失。⚠️ **`SIGTERM` 停不下来**，因为 `KeepAlive` 为真: launchd 安排了重启（`state = spawn scheduled`、`last exit code = 0`），守护进程大约十秒后回来了。**停止是 `bootout`，杀掉是重启。** ⚠️ **那道节流是一扇听不见的窗**——在它里面到达的事件被丢弃，按客户端自身的设计。

**要卸下它:**

```
launchctl bootout gui/501/embodied-kinetic-loom.stackchan
rm ~/Library/LaunchAgents/embodied-kinetic-loom.stackchan.plist
rm -f /tmp/ekl-stackchan-501.sock /tmp/ekl-stackchan-daemon.log /tmp/ekl-stackchan-daemon.err
```

然后从 `~/.claude/settings.json` 里去掉 `hooks` 键。⚠️ **其他什么都不碰**: 守护进程只写套接字和那两个日志，而且它不向任何机器发送。

## 什么会响，什么不会

✅ **这一页的一部分会响。** 纯的部分在没有套接字的情况下被检查——请求的模式、未知键的拒绝、以及给定 `(session, event, at)` 的决定——而套接字作为一个真实的进程被检查: 它作答、拒绝、把返回的行写进日志，并在 `SIGTERM` 时干净地退出。**二十六条主张都在 `tests/test_stackchan_daemon.py` 里**——最后两条是: 问候写下 `sent: false` 的一个帧行，而不变的事件一个也不写。 ✅ **另有二十一条守住客户端**——输入里的提示词、cwd 与工具输入到不了那一行，未知事件在套接字之前被丢弃，路径只有一种拼写，而永不回应的对方也不会让它迟延——**在 `tests/test_stackchan_hook_client.py` 里。**

⛔ **没有一个测试检查安装。** launchd 的 `RunAtLoad` 与 `KeepAlive`、登录与登出、plist，以及重启后出现的陈旧套接字，都是操作系统的行为，不是一个函数。✅ **取而代之的是上面写下的一次观察**: 2026-10-18，安装好的作业把一条真实的钩子链从头到尾跑了一遍，并被用手停止和重启。⚠️ **在一台主机上的观察不是检查**——它不会再跑，也不会在应该失败的时候失败。`tools/check_i18n.py` 仍然只确认三份副本一致。
