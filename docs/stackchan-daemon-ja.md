# スタックチャンのデーモン — 起動と停止

✅ **ループとソケットとクライアントは作られた——2026-10-18。** `projects/stackchan/daemon/` が純粋な中核（`room.py`）と縁（`__main__.py`）を持ち、`projects/stackchan/hook/` がフックの走らせるクライアントを持ち、`tests/test_stackchan_daemon.py` が前者について41の主張を、`tests/test_stackchan_hook_client.py` が後者について21の主張を持つ。✅ **そして同じ日に導入された**——launchd のユーザーエージェントがログイン時にデーモンを起動し、33のフック事象すべてがクライアントを呼ぶ。**導入は1つのホストの上の場所であり、リポジトリの性質ではない**（[導入の、いまの姿](#導入のいまの姿)を見よ）。

⚠️ **何のために在るか。** Claude Code のフックは1事象につき1プロセスであり、`Focus` と `Companion` は事象と事象のあいだ生き続けなければならない1つの物体である。デーモンはその物体に、時計とソケットを足したものである。それは連鎖の中段——**フック → デーモン → 電線 → ファームウェア**——であり、ロボットを「開いている端末のもの」ではなく「部屋のもの」にする部品である。

✅ **1つのホストに導入されており、リポジトリが持つのはジョブの複製であって、ジョブそのものではない。** `projects/stackchan/launchd/embodied-kinetic-loom.stackchan.plist` がそのファイルであり、2つの絶対パスでこのホストを名指ししている。生きている複製は `~/Library/LaunchAgents/` に在る。⛔ **リポジトリの中の plist は、走っているデーモンではない**——導入は `launchctl bootstrap` であり、外すのはその逆である。`tools/check_i18n.py` は写しが一致するかを見るだけで、設計を見ない。**2つのプロセスは `tests/test_stackchan_daemon.py` と `tests/test_stackchan_hook_client.py` が見ており、導入は何も見ていない。**

## なぜ状態がホストに住むか

⚠️ **別案は検討された: 段階・注視・タイマーをファームウェアに置き、電線に身振りではなく事象を運ばせる案である。** それは選ばれなかった。理由をここに残すのは、**省略は中立ではない**からである。

⛔ **2つの設計は電線で分岐する。** 状態がホストにあれば、電線は**身振り**を運ぶ。状態がファームウェアにあれば、**事象と窓の名前**を運ぶ。**すでに決まっている電線は身振りを運び**、0.19.0 の契約はそれに対して書かれている。⇒ **後から状態を移すのは移植ではなく、プロトコルの変更である。**

**機体側の設計が買うもの:** 常駐プロセスが一切無いこと——launchd も、ソケットも、錠も無い; Mac の再起動をまたいで残る状態; 複数のホストから1つの体に集められること; そして**このリポジトリがディスクに無くても走る振る舞い**。

**いま払う代価:** カスタムファーム——この工房で最も閉じた段であり、復元の経路はいまや書かれ、読み戻され、起動するのまで見られており、NVS のゼロ点は一度すでに動いている; **同じ規則の C++ による2つ目の実装**——このリポジトリの試験はそこに届かず、しかもこのリポジトリは一覧を2つ書くことを欠陥と呼ぶ; 振る舞いを変えるたびの再書き込み; そして、まだ存在しない電線越しのデバッグ。

⚠️ **機体側の設計が買うとよく思われていて、買わないもの:** ホストが消えても働き続けるロボット。**死んだデーモンはすでに暴走したロボットではない**——何も流れ続けず、待機はファームが所有する。どちらでもロボットは自分の振る舞いに戻る。状態がホストにあることで本当に失われるのは、もっと狭い: **リポジトリがディスクに在ること**と、**デーモンの再起動をまたいで段階が残らないこと**である。

⚠️ **この決定は、次のどれかが要求になったときに開き直される:** このリポジトリが無い状態での振る舞い; ホストの再起動をまたぐ状態; 複数のホストが1つの体に集まること; 常駐プロセスが一切無いこと。**今日、そのどれも要求ではない。**

## 起動と停止は、機体の起動と停止ではない

⚠️ **ファームウェアの待機の振る舞いは、ファームウェア自身のものである。** デーモンは決定を足すが、体を所有しない。⇒ **デーモンを起動してもロボットは起動せず、停止してもロボットは駐機しない。** これが効くのは、機体1のプロトコルに停止命令が無く、機体2のプロトコルはここでは一切確定していないからである。

⛔ **死んだデーモンは、暴走したロボットではない。** これは身振りコマンド設計の性質である: 何も流れ続けない。ファームウェアが最後に告げられたのは1つの身振りであり、その始まりと終わりはファームウェアが所有する。デーモンが死んだとき、届き続けるものは無い。

## ライフサイクル

| 状態 | 入るきっかけ | 何が真か |
|---|---|---|
| `stopped` | ログイン前、`bootout` の後、正常終了の後 | ソケット無し、状態無し |
| `starting` | launchd、または手動の実行 | ソケットは bind 済み。**まだ何も送っていない** |
| `ready` | bind の成功 | ループはソケットと次の期限を待つ |
| `stopping` | `SIGTERM` または `SIGINT` | 新しい事象は受けない。閉じる。終了コード 0 |
| `stopped` | 終了 | ソケットは unlink される |

⚠️ **永続化は無い。** 段階、タイマー、注視、失敗の数は、すべて `present` からやり直しになる。**再起動したデーモンは再開しない**: 次の遷移が段階を立て直す。代価は名指しする: ターンの途中で再起動すると、ロボットはターンが続いているのに `present` を示す——次の遷移まで。

⚠️ **起動は挨拶を送らない。** 最初の運動は最初の事象から来るのであって、デーモンが生きていることからは来ない。**「こんにちは」は機体のための運動である**——`working` のあいだ体を止めておくのと同じ規則である。

## 誰が起動するか — フックではなく launchd

✅ **macOS のユーザーエージェント**（`LaunchAgents`）で、`RunAtLoad` と `KeepAlive`。理由は3つ:

- **ログイン時の起動**: 利用者は何も開かない。それがこの頁をここに置いた要求である;
- **異常終了時の再起動**: ソケットのクライアントにはできない;
- **所有者が1つ**: ライフサイクルは1か所に住み、フックに散らばらない。

⛔ **フックはデーモンを spawn しない。** spawn するフックは記憶を持たない監督である: 同時に届いた2つの事象が競合し、フックから起動されたデーモンはそのフックの環境を引き継ぐ。**フックは伝令であり、監督ではない。**

⚠️ **ソケット起動だけでは足りない**（launchd にはその機能があるが）: 事象が止まったらロボットは眠らなければならず、**眠るには期限に気づく生きたプロセスが要る**。デーモンは生き続けて待つ。

⚠️ **ラベルは `embodied-kinetic-loom.stackchan`**——文字列であり、ドメインではない。逆引き DNS は発明しない。ジョブは `WorkingDirectory` をリポジトリのルートに、絶対パスのインタプリタで走る。launchd はジョブを自分自身の作業ディレクトリ無しで起動するからである。

## 単一インスタンスと、古いソケット

⚠️ **ソケットが錠である。** そのパスは `/tmp/ekl-stackchan-<uid>.sock` で、bind の後にモード `0600` にする——ソケットファイルはプロセスの umask を引き継ぐからである。短いパスは体裁ではない: macOS の `sun_path` は104バイトで、`/var/folders/…` の下の `$TMPDIR` は、長いユーザー名ではその限界に届いて壊れる。

⚠️ **起動は bind の前に探る:** 先にパスへ connect する。connect が成功すれば、**別のデーモンが生きており、このプロセスは機体に一言も告げずに終了する。** `ECONNREFUSED` または `ENOENT` で失敗すれば、パスは古い——unlink してから bind する。

⛔ **pidfile は無い。** pidfile は古びることがあり、探れない。ソケットは答えることができる。**錠は1つ、2つではない。**

## フックが送るもの

**1事象につき JSON 1行:**

```
{"session": "<session_id>", "event": "<hook_event_name>"}
```

⛔ **プロンプトはメッセージの中に無く、スキーマは知らない鍵を拒む。** 無視されるだけの欄は同乗できる。拒まれる欄は同乗できない。**政策ではなく、構造によるプライバシー。**

⚠️ **クライアントは時刻を送らない。デーモンが行の到着時に刻む**——単調時計で。理由は2つ: クライアントは状態を持たない伝令であり、逆行する壁時計は層が拒む嘘である。**`Decision` の中の時刻はデーモンのものであり、フックのものではない。**

⚠️ **クライアントは100 ms 待ち、どの失敗でも静かに終了コード 0 で終わる。** フックはターンを塞いではならず、ロボットをエラーに変えてもならない。**取りこぼした事象は捨てられ、行列に並ばない**: 遅れて届いた事象は、いつ起きたかについての嘘であり、次の事象が段階を、待機の時計が残りを直す。

⚠️ **代価を名指しする:** `SessionStart` のときにデーモンが落ちていれば挨拶は無く、ロボットは次の遷移まで `present` を示す。`SessionEnd` のときに落ちていれば、ロボットは待機のタイマーで眠る。どちらも痕跡に見え、どちらもエラーではない。

✅ **クライアントそのものが、いま在る**——`projects/stackchan/hook/`、1事象につき1プロセス。標準入力を読み（上限 1 MiB）、**`session` と `event` だけを組み直す**のでプロンプトは同行できず、行を送り、**返事を読まず**、何も印字せず、どの失敗でも 0 で終わる。**デーモンの不在は、フックの失敗ではない。** ✅ **2026-10-18 から呼ぶ側が在る: `~/.claude/settings.json` の33の事象すべてがそれを走らせる**（[導入の、いまの姿](#導入のいまの姿)を見よ）。

## 待つループ

⚠️ **ポーリングしない。** デーモンはリスナーの上で、次の期限に等しいタイムアウト付きで待つ——`min(hold_until, idle_until, quiet_until)`——そして `settled` または `slept` の決定を、それが来るべき瞬間に起こされて出す。**これは間隔を1つも発明しない**: 層に tick の定数は加わらない。

⚠️ **1度に1事象、accept ループが取った順に。** 行列も、並べ替えも無い。行を同じ100 ms のうちに届けない接続は閉じられる。**数は1つ、1か所で名づけ、両端で使う。**

⚠️ **時計は単調である。** CLI の台本の時刻は別の領域——台本からの秒——であり、層の契約はどちらでも同じである: `offer(session, event, at)` は値を受け取り、時計を決して読まない。

## 停止と、体がすること

⛔ **`SIGTERM` でデーモンは送るのをやめる。駐機も、落ち着きも、最後の身振りも送らない。** 安全に送れるものが無い: この機体に停止命令は無く、停止時に発明された身振りは、誰も選ばなかった唯一の運動である。

⚠️ **サーボを放置すれば首は垂れることがある**——SCS サーボは待機時にトルクを放す。**それは機体の待機の振る舞いであり、故障ではない。** 手元の個体で見られている。

⚠️ **デーモンが止まった後、ファームウェアが最後の顔をどうするかは、ここでは決まっていない。** ファームウェアが保持するなら顔は残り、ファームウェア自身の待機が引き継ぐなら変わる。⛔ **0.19.0 の契約もまた、それを決めていない**——契約が運ぶ `face: null` は「変えない」であり、行が届かないとき基板が何をするかについては何も言わない。

## 機体は任意である

✅ **デーモンは機体無しで走る**——そしてそれは今も既定である: `--port` が無ければ、枠を符号化してログの1行として書くだけである。✅ **2026-10-18 から、その行を基板のコンソールへも書ける**、そして導入済みのジョブはそうしている——[伝送路](#伝送路)を見よ。

⛔ **機体のエラーは記録して捨て、決して致命にしない。** `KeepAlive` の下では、機体の不在と致命的エラーが揃えばクラッシュループになる——**監督は、待つはずのものを殺し続けることになる。** ⚠️ **存在しない経路はその場合であり、しかもよくある方である**: コンソールの名前は抜き差しで変わるので、行は `sent: false` になり、部屋はそれでも事象に答える。

## 枠を書き、——ポートを与えられれば——送る

✅ **0.19.1 から、すべての決定が `projects/stackchan/outbound.py` を通り**、枠が `None` でないとき、デーモンはそれを1行として書く:

```
{"frame": "{\"face\":null,\"gesture\":null,\"light\":\"breathe\",\"sound\":null}", "sent": false, "at": 6497.584270416, "session": "…"}
```

- **枠は、機体の見せるものが変わったときに書く**——顔か光——**か、身振りが選ばれたとき、か、音が名指されたとき、か、そのプロセスの最初の決定であるとき。** ✅ **4番目の鍵は 0.19.13 に来た**——必須であり、`null` は*この枠は黙る*を意味する。⛔ **最後のものを保て、ではない。** **音は事象であり、身振りも事象であり、顔と光は状態である**——枠のあいだ覚えられるのは状態だけである。
- ⚠️ **音は既定で切れている**（`--sound on|off`）。著者の決定であり、これを入れたことで機体が頼まれずに喋り出してはならない。✅ **0.19.26 から、設置済みのジョブは `--sound on` を名指す**——著者が 2026-10-19 に求めたのであり、昼は喋り夜は喋らない; ⛔ **ジョブは時を名指さない**、時は `quiet.py` に属し、他のどこにも属さないからである。 ✅ **そして 0.19.25 から、スイッチだけでなく時刻がある**: `projects/stackchan/quiet.py` がこの時は 21:00–05:00 かを答え、縁が事象ごとに壁時計を1度読み、`Room.offer(..., quiet=True)` が `sound` の欄だけを閉じる——⛔ **顔・光・首はそのままであり、中核は今も時計を読まない。** ⚠️ **境界は正時である**: 20:59 は昼、21:00 は静か、05:00 はまた昼。⛔ **スイッチが切れていても、鍵は `null` として書かれる**——枠の形はどちらでも同じであり、基板が「なぜ鳴らなかったか」を推し量ることはない。⛔ **最初の決定は必ず出す。その前の機体の状態が知られていないからである**; 顔は枠自身の状態から埋めるので、機体は自分が何を映していたかを憶えておかなくてよい。
- ⛔ **事象の理由は状態の変化を仕切らない**ので、規則は理由ではなく状態を読む。`blocked` の中の `PostToolUse` は、理由 `OBSERVED` で `working` へ戻り、光は動かないことがある; 懸念は光を変え、段階を変えない。
- ⚠️ **これは流れではない。** 観測された走りでは、最初の枠に続いた `PreToolUse` は2行目を書かなかった。
- **その行は符号器のものである**——`engine/backend/protocol_stackchan.py`、`tests/test_stackchan_wire.py` が押さえるのと同じもの——だから**ログが `schemas/stackchan-command.schema.json` からずれることはない。**
- ✅ **0.19.28 から、ログには読み手が居る**——`python3 -m projects.stackchan.day <path>` が、その中身を数える: 行、起動、判定、枠とその送信の有無、流した身振り（予定・適用・遅れ・保持）、読み戻し（**heard** と **positions** を別々に）、そしてポートに届いた枠それぞれの語である。**中核は行を受け取り、ファイルも時計も読まない**（`day/summary.py`、19のテスト）; **縁が開くパスは1本であり、既定値は無い**——設置済みのジョブがログを1度だけ名指しており、2つ目の綴りは古くなる側である。⚠️ **読み戻しと判定の数は、デーモンが書く形の行から数える**（0.19.38 から探針の行は1つの形であり、流しの判定はホスト自身の `applied` と別の欄で数える）; ⛔ **下の数はその両方の変更より前の 05:36 に取られたものであり、「位置を返したもの 0」は欠陥であって機体ではなかった。** **2026-10-19 05:36 の測定: 3,852行、起動 11、判定 3,599、枠 124（すべて `sent: true`）、流れ 48——予定 1,564、適用 1,518、遅れ 1,316、保持 1,256——読み戻し 24（聞こえた 12）、音 2（`hello`、`chime`）。** ⛔ **読み手は再起動を数えられても、理由は言えない**: 113分に11回の起動があり、stderr には1行も無い。
- ⛔ **ログの1行は電線ではない**、そして ⛔ **運動の記録でもない**——その要件は `CLAUDE.md` にあり、形は、そこへ入れるものができた日に決まった。✅ **2026-10-18 から、ポートが名指されれば同じ行がポートへも書かれ、1つの符号化が両方を養う**——ログの行も電線の上のバイトも、符号器への1回の呼び出しから来る。

## 伝送路

✅ **2026-10-18 に決まり、測られた。** `--port PATH` が基板のコンソールを名指しする。与えられれば、枠の行の1行ずつがその経路へも書かれるので、部屋が静かなあいだは `bench` と `idf.py` が依然ポートを持つ。⚠️ **書く形は2つあり、2026-10-19 にハングがそれを割った。** **枠は今も `os.open` 1回、`os.write` 1回、`os.close` 1回で、枠と枠のあいだはポートを保持しない。** ⛔ **姿勢の流れはその形では書けない**——50 Hz で open/write/close を繰り返すと、デーモンは `open()` の中で固まり、そこへは信号が届かない——ので、0.19.15 以降**流れはポートを1度だけ開き、1つの身振りの長さだけ保持し、要約で閉じる。**

- ⛔ **固まりは、推測ではなく測られた。** 2026-10-19、導入済みのデーモンが答えなくなった: `ps` は状態 `U` を示し、`sample` はスレッドを `open()` の中に置いた。2通りに再現した——open/write/close の繰り返しは4度目か5度目の `open()` で塞がり、閉じない非ブロッキングの書き手は基板が排出を止めるたびに68行（約1 KB）まで通してから `EAGAIN` になった。⇒ **ホストはこのコンソールを繰り返し開いてはならず、基板は排出を止めうる; どちらも告げられない。** ⚠️ **基板は、著者がケーブルを抜いて差し直すまで沈黙していた**; その後、基板自身のコンソールは再び答えた。
- **流れの書き込みには、どれも上限がある**——`PORT_WAIT = 0.5`。0.5秒で終わらない書き込みは流れを終わらせ、`{"neck": …, "sent": false, "at": …}` として記録される; そもそも開けないポートは身振りを基板に委ね（`gesture` は枠に残る）、部屋はそのまま続く。**流れは要約の後には何も保持しない。**
- ✅ **到着を言うのは基板の文である。** 2026-10-19、デーモンが書くあいだ読み取り手を付けて、流れを機体で再生した。基板は `pose: stream started — goals on the present positions (yaw 504, pitch 780), torque on` と印字し、沈黙の後に `pose: stream lost after 500 ms — torque released` と `pose: 23 applied, 0 refused, 0 clamped` と印字した。**その身振りについてデーモン自身の要約は `{"neck": "look_side", "applied": 23, "late": 19, "held": 29}` だった。** ⛔ **23のうち19が遅れて当たった**——基板の主ループはまだ前の身振りの中にいた——そして**首が目に見えて動いたかどうかは、まだ書かれていない。**
- **`sent` が `true` になるのは、`os.write` が全長を返したときだけである。** ⛔ **それはホストの tty がバイトを受け取ったという意味であり、基板が受け取ったという意味ではない**——そしてこの日、その2つの主張は1時間のあいだ離れていた: `sent: true` を名乗る行がログに在るのに、機体の側は何も答えなかった。
- ⚠️ **到着を証明するのは、行ではなく基板である。** 2026-10-18 に1度だけ証明された——デーモンが書くあいだ、コンソールを `os.open` と生の `termios` で読んで:

```
frame: light=warm face=greeting (no renderer yet)
frame: gesture perk refused — no gesture -> angle table exists
```

  ⇒ **デーモンのログは `{"face":"greeting","gesture":"perk","light":"warm"}` を `"sent": true` 付きで保持し、基板は同じ語を印字した。** ⛔ **身振りはその日に拒まれた**——`command_frame.cpp` は角度が測られるまですべての身振りを拒み、測られたのはその日のうちだった——**そしてその拒否は光を止めなかった。** ⚠️ **そのログの語は、当時のプロトコルが運んでいた語である**: 著者が 2026-10-18 のうちに5つの身振りすべてを改名したとき、`perk` は `look_up` になった（`projects/stackchan-firmware/records/2026-10-18-the-gestures.md`）。⚠️ **その2行は4番目の鍵より前のものである**ので、どちらも `sound` を運ばない; 0.19.13 以降に書かれた枠は必ず運ぶ。
- ⚠️ **経路は身元ではない。** 1台の基板で、ハングの前は `/dev/cu.usbmodem1101`、1度の抜き差しの後は `/dev/cu.usbmodem101` だった——**16分違いである。** 導入済みの plist は2つ目を名指しする; **抜き差しが3つ目を名指ししても、デーモンは `sent: false` を記録して続ける。** ⇒ **この導入についてケーブルが無効にできるのは、plist のポートだけである。**
- ⛔ **ここでは行を行列に入れない。それは限界でもある**: 他のプログラムがポートを持つあいだに書かれた枠は、送られなかったものとして記録され、書けない流れは待つのではなく止まる。**どちらにせよ、部屋は事象に答える。**
- ⚠️ **DTR と RTS を立てる読み取り手は、リセットである。** `pyserial` でこのコンソールを開くと基板は起動途中にリセットし、ケーブルを抜き差しするまで ROM は答えなくなった; **デーモン自身の `os.open` の経路を単独で走らせたときは、どちらも起きなかった。** このコンソールを見たいときは、`os.open` と生の `termios` を使うこと。
- ⛔ **2人の書き手の行は、混ざりうる——そして基板は1行として読む。** 2026-10-19、設置済みのデーモンが走っているあいだに測った: 2つ目の `os.open` から書いた `bench scan` は、コンソールに `frame: refused (malformed)` を出させ、走査は1つも走らなかった; 同じコマンドを 0.3 秒後に書くと、普通に走査した。⚠️ **機構は確定していない**——どちらの書き込みもエラーを返さず——**だが、基板が malformed として拒む行は `{` で始まる行だけであり**、その行を書く者はデーモンだけである。⇒ **コンソールは共有された時間であり、安全に共有された場所ではない: 外からの問い合わせは枠を裂き、枠はどちらの側にも気づかれずに失われる。** ⛔ **デーモン自身の `bench pos` がこれを避けるのは、錠を取るからではなく、これから流す fd を使うからである。**

⚠️ **どの検査も覆っていないこと:** 下のポートの7つの試験は、機体ではなく**普通のファイル**を開く。⛔ **ポートを開く試験は1つも無く**、存在しない経路は機体のエラーではなく `sent: false` として試され、上の到着の測定は1つのホストでの1つの観察である。

## 決まったこと、決まっていないこと

**ここで決まったこと:**

- launchd のユーザーエージェント、`RunAtLoad` と `KeepAlive`。ラベルは `embodied-kinetic-loom.stackchan`;
- `/tmp/ekl-stackchan-<uid>.sock`、モード `0600`、探ってから bind、pidfile 無し;
- デーモンが刻む単調時刻。クライアントの時刻は無し;
- JSON 1行、知らない鍵は拒み、プロンプトは構造的に不在;
- クライアントの100 ms 待ち、失敗したら捨てる、行列無し;
- 次の期限を待つ。固定の tick は無し;
- 挨拶無し、駐機無し、永続化無し;
- 機体の連結は任意で、決して致命でない。

**ここで決まっていないこと:**

- ✅ **枠は決まった（0.19.0）。そしてこの頁は、いまもそれを所有しない**——ASCII の JSON 1行、`face` / `light` / `gesture` / `sound`、`schemas/stackchan-command.schema.json` にあり、`engine/backend/protocol_stackchan.py` が符号化する。✅ **0.19.1 からデーモンはその符号器を呼び、渡すはずの行を書く。** ✅ **0.19.8 から伝送路も決まった: デーモンはその行を基板のコンソールへ書き、枠ごとに1回開き、導入済みの plist が経路を名指しする**（[伝送路](#伝送路)を見よ）。✅ **そして同じ日のうちに、`projects/stackchan-firmware/` は受け取った身振りを演じる**——この個体で測った5つの姿勢——**ので、身振りを運ぶ枠が頭を動かす**（`projects/stackchan-firmware/records/2026-10-18-the-gestures.md`）; ✅ **そして 0.19.11 から、エンジンは著者が受け入れるほど滑らかにこれを動かす**——ファームの書き方を純正自身の呼び出しに変えたあとの `projects/stackchan/neck/`（`records/2026-10-18-the-neck.md`）;
- 待機時と停止後にファームウェアが何をするか;
- 2つ目の体——機体ごとの2つ目のデーモン——が何か違うものを要するか。

## 導入の、いまの姿

**2026-10-18 に、作者の Mac（uid 501）で測られた。** これは設計ではなく、何をし、何を見たかの記録である——試験でもない。

- **ジョブ。** `~/Library/LaunchAgents/embodied-kinetic-loom.stackchan.plist` を `gui/501/embodied-kinetic-loom.stackchan` に bootstrap した。`RunAtLoad` と `KeepAlive` は真、インタプリタは絶対パス（`/opt/homebrew/bin/python3`）、`WorkingDirectory` はリポジトリのルートである。**`projects/stackchan/launchd/` の複製は同じファイルである。**

- **ポートを、名指した（2026-10-18）。** plist は `--port /dev/cu.usbmodem101` を渡し、導入されたジョブは枠ごとに基板のコンソールへ書く。**このリポジトリの枠が伝送路を通って機体へ届き、両端が観測された最初の1つは、[伝送路](#伝送路)に引用されている。** ⛔ **経路は抜き差しの前は `/dev/cu.usbmodem1101`、後は `/dev/cu.usbmodem101` だった**; 経路が消えれば行は `sent: false` になり、他には何も変わらない。

rm ~/Library/LaunchAgents/embodied-kinetic-loom.stackchan.plist
rm -f /tmp/ekl-stackchan-501.sock /tmp/ekl-stackchan-daemon.log /tmp/ekl-stackchan-daemon.err

## 何が鳴り、何が鳴らないか
