## ⛔ 1時間を溶かす罠——そして、それは「壊れた基板」に見える

**ポート名は身元ではなく、安定もしない。**

- **Fresco Logic の USB ハブ**（Realtek Ethernet 付きドック）を経由すると、**列挙は正しいまま、シリアルだけが完全に死ぬ。** `/dev/cu.usbmodem*` は現れ、USB の文字列も MAC も正しく読める——**そのうえで:** esptool は全リセットモードで `No serial data received` を返し、pyserial は**全ボーレートで 0 バイト**、一部のレートでは `OSError: [Errno 83] Device error` が上がり、**ブートログは1行も出ない。**
  ⛔ **これは「基板が死んだ」と誤診される形である。** 直し方は **Mac 本体に直挿しする**——そして `Mac14,10` には USB-A が無いので、**データ対応の USB-C ↔ USB-C ケーブル**が要る。
- **名前は動く。** ハブを外すと、個体は `/dev/cu.usbmodem1401` から `/dev/cu.usbmodem1101` へ移った。⚠️ **そして 10/04 の記録同士が、`/dev/cu.usbmodem101` と `1101` のどちらがスタックチャンだったかで食い違っている。**

⇒ **個体は MAC で識別すること。ポート名では決して識別しない。** ⚠️ **現れた経路は、通る経路ではない**——**そして「列挙できている」は、まさにそれを信じてしまう場合である。**

## ⛔ このエンジンと衝突する、実測が1つある

⚠️ **これは、何かを周期で送る前に、あなたを止めるべき行である。**

## ここでの「止める」とは何か

⛔ **この機体にも、止めるコマンドは無い。**

⇒ **実際に使う停止は、電源スイッチか、バッテリーである。** **ポートを開く前に、それがどこにあるかを知っておくこと**——**そしてこの個体では、USB-C ケーブルを挿す前に、である。10/04 の個体では、生きていたのは「焼く」経路のほうだった。**

## ⛔ 誤読してはならない結末

⚠️ **この機体では、機体1よりも「緑のログ」の結末に到達しやすい。そしてそれこそが、危険である理由である。**

⇒ **あちらと同じである: 緑のログが持てるのは、ホストから出たものと、電線から戻ってきたものである。そのどちらも「動いた」ではない。**
