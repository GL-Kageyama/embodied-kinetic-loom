⛔ **そして、反対側から始まる。** 機体1の頁では、**項目は1つも行われていない**——機体が無かったからである。**ここでは、ほとんどが既に行われている**——**手元の個体は 2026-10-15 に計算機の前に置かれ、もう1台は 2026-10-04 に動かされた**——**そして、両者は同じ機体ではない。**

⇒ **この頁の警告は、あの頁の警告の裏返しである。** あちらでは、整いすぎた一覧が「片づいた」ように読めうる——**1つも片づいていないのに。** **こちらでは、整いすぎた一覧が「答えは手元の個体のものだ」のように読めうる——そして、ほとんどはそうではない。** ⚠️ **以下の事実はすべて、どの個体で測られたかを名乗る。** **片方の個体の事実は、もう片方の事実ではない。**

## ファームを焼く門は、1つである

**純正のイメージを書き戻せるか。** これを最初にやる——⛔ **焼くことは、この頁で唯一、そのあとに何を送っても取り消せない行為だからである。**

安全網は在り、そして検証されている:

| | |
|---|---|
| ファイル | `backup/stackchan-stock.bin`——⚠️ **Desktop に在り、このリポジトリには無い** |
| 長さ | **16,777,216 バイト** |
| SHA256 | `012fe9d0b3c6075f78dd5426d5da7ed451c96c77ff685b1540c33a1f7594b466` |
| MD5 | `57de1620c3d1d4653927382abc7528d5` |
| 読み戻し | ✅ esptool の `verify-flash` が、**デバイスとビット単位で一致**と報告した |
| 復元 | `esptool --port /dev/cu.usbmodemXXXX write-flash 0 backup/stackchan-stock.bin` |

eFuse の実測: **`SECURE_BOOT_EN` False**、**`SPI_BOOT_CRYPT_CNT` Disable**、**`DIS_DOWNLOAD_MODE` False**、**`DIS_USB_SERIAL_JTAG` False**、そして `SOFT_DIS_JTAG` / `DIS_PAD_JTAG` は無効化されていない。⇒ **ロックは1つもかかっておらず、自作のイメージを焼ける。**

⛔ **そして、安全網が覆っていない部分がここにある。** ⚠️ **記録には、書き込みが1つも無い。** イメージはフラッシュを**読んで**作られ、**もう一度読んで**確認された。⇒ **書き込みの経路——ケーブル、チップ、ドライバ、オフセット——は、このホストで一度も通っていない。** **読みの検証が証明するのは「イメージはこのデバイスのものである」ことである。「イメージを戻せる」ことは証明しない。**

⇒ **最初の自作曲を焼く前に、復元を1回行うこと。** 純正のイメージを書き、起動させ、版を読み戻す。**そこで初めて、網が保つと分かる。** ⛔ **一度も張られていない安全網は、網ではなくファイルである。**

⚠️ **そして、何かを押す前に決めることが1つある——サーボのゼロは NVS に住んでいる。** **イメージ全体の復元は 455 / 603 に戻す**——⚠️ **2026-10-15 にウィザードが書いた 460 / 620 には戻さない。** ⛔ **パーティションだけの復元は、また別の何かに戻す。** ⇒ **3つのどれを選ぶのかを分かっておくこと。そして、その選択を焼く前に書き残すこと——後にではなく。**

## ⛔ 1時間を溶かす罠——そして、それは「壊れた基板」に見える

**ポート名は身元ではなく、安定もしない。**

- **Fresco Logic の USB ハブ**（Realtek Ethernet 付きドック）を経由すると、**列挙は正しいまま、シリアルだけが完全に死ぬ。** `/dev/cu.usbmodem*` は現れ、USB の文字列も MAC も正しく読める——**そのうえで:** esptool は全リセットモードで `No serial data received` を返し、pyserial は**全ボーレートで 0 バイト**、一部のレートでは `OSError: [Errno 83] Device error` が上がり、**ブートログは1行も出ない。**
  ⛔ **これは「基板が死んだ」と誤診される形である。** 直し方は **Mac 本体に直挿しする**——そして `Mac14,10` には USB-A が無いので、**データ対応の USB-C ↔ USB-C ケーブル**が要る。
- **名前は動く。** ハブを外すと、個体は `/dev/cu.usbmodem1401` から `/dev/cu.usbmodem1101` へ移った。⚠️ **そして 10/04 の記録同士が、`/dev/cu.usbmodem101` と `1101` のどちらがスタックチャンだったかで食い違っている。**

⇒ **個体は MAC で識別すること。ポート名では決して識別しない。** ⚠️ **現れた経路は、通る経路ではない**——**そして「列挙できている」は、まさにそれを信じてしまう場合である。**

## 機体2が答えていること——そして、答えたのはどの個体か

⚠️ **これらは、機体1の頁がいまも「不明」として並べている問いである。ここには答えが在る——10/04 の個体についてのものと、手元の個体についてのものが混ざって。**

- **軸はいくつか。** **2つ**——yaw（サーボ ID 1）と pitch（ID 2）。⛔ **roll は無い。** `Motion Intent` の3つの名前は変わらない——**この機体が、そのうち1つを持たないだけである**——**そしてそれを書き留める場所は、語彙の「差」の欄である。**
- **数の単位。** **入りは度、出はサーボのカウント。** ⛔ **そして両者の換算は、どの記録にも無い。** 記録に在るのは**ゼロ点**であって、**スケールではない。**
- **数が何をするか。** 10/04 の個体では: `head 45 90` → yaw 322、`head 90 90` → 454、`head 135 90` → 597、`head center` → 454。`head 90 45` → pitch 637、`head 90 90` → 762。✅ **1軸について3点、そして間隔は均等である**——⚠️ **その個体での話である。** ⛔ **手元の個体へ持ち込まないこと:** 手元のゼロ点はウィザードに 460 / 620 へ書き換えられており、**そしてゼロ点はスケールではない。**
- **伝送路。** **両方の個体とも** ESP32-S3 の **native USB Serial/JTAG**——VID `0x303A` / PID `0x1001`。⛔ **CP210x も CH9102 も無い**——ゆえに回線設定も自動リセットの挙動も、USB-UART ブリッジのものではなく ESP32-S3 のものである。
- **シェルに言えること。** `head nod|shake|center|<pan> <tilt>`、`vmen on|off`、`track on|off|mirror`、`follow`、`search`、`say` / `greet` / `tts`、`brain <url>`、`wifi` / `scan` / `target` / `gw`、`rover`、`i2cint` / `camtest`、`status` / `ping` / `clear` / `reboot`。⚠️ **これは 10/04 の個体のシェルであり、もう一方のファームに付いてきたものである。** ⛔ **手元の個体にシェルは無い。**
- **フラッシュの配置**（10/04 の個体）: nvs 20 KB、otadata 8 KB、app0 3072 KB、app1 3072 KB、ffat 10112 KB、coredump 64 KB。⚠️ **配置が同じことは、ファームが同じことではない**——手元の個体は `0x510000` のスロット `ota_1` から起動している。

## ⛔ このエンジンと衝突する、実測が1つある

⚠️ **これは、何かを周期で送る前に、あなたを止めるべき行である。**

10/04 の個体に向けて書かれたサンプルゲームからの逐語:

> サーボが動き切る前に次の指令を送ると、サーボがストールして電源レールが落ち、**両軸とも無応答になる。** 移動を伴う指令は必ず 1 秒以上あけること。（`MOVE_SETTLE = 1.0`）

⛔ **そしてこのエンジンは、15〜20 ms ごとに目標を送り続ける機械として作られている。** **それがこの機体で耐えられるかは測っていない**——そして記録に在る唯一の点は、逆側を指している: `head 90 135` が**サーボをストールさせ、レールを落とし、両軸を `yaw=-1 pitch=-1` にした。** 復旧は `vmen off` → `vmen on` で、**3回中3回成功した。**

⇒ **この経路の周期・速度上限・可動域は、すべて未測定であり、既定値を持たない**——機体1の `Envelope` と同じ規則である: **誰も測っていない数は既定値ではない。既定値の服を着た推測である。** ⚠️ **そして、それに答えられるのは門だけである**——門が「速すぎる1フレーム」を弾けるのは `velocity` があるからである。**その数が無い門は、何も守らない。**

⚠️ **そして、何よりも先に `track off` を送ること。** カメラの顔追跡が `cam_hal: EV-VSYNC-OVF` でストリームを溢れさせ、**シェルが応答しなくなる。** **それがファームのせいなのかカメラのせいなのかは記録に無い**——**だが 10/04 の個体では、追跡を切るまでシェルは壊れて見えていた。**

## ここでの「止める」とは何か

⛔ **この機体にも、止めるコマンドは無い。**

| コマンド | 実際に何をするか |
|---|---|
| `vmen off` | **サーボ電源**を切る——⚠️ **そして電源の無いサーボは、どの位置も保持しない** |
| `reboot` | ⚠️ **再起動は停止ではない**——レールが戻り、サーボは最後に言われた値へ戻る |
| 「その場で止まれ」 | **そんなコマンドは無い** |
| ケーブルを抜く | ⛔ **機体1と同じ罠である**——**ホストが去ったからといって、機体は止まらない** |

⚠️ **そしてここは、機体1より良いどころか悪い。** あちらでは、故障モードはトルクが4分の1に落ちることだった。**こちらで記録されている故障モードは、レールそのものが落ちることである**——⛔ **つまり、命令していなかった軸が、命令していた軸と一緒に落ちる。**

⇒ **実際に使う停止は、電源スイッチか、バッテリーである。** **ポートを開く前に、それがどこにあるかを知っておくこと**——**そしてこの個体では、USB-C ケーブルを挿す前に、である。10/04 の個体では、生きていたのは「焼く」経路のほうだった。**

## ⛔ 誤読してはならない結末

⚠️ **この機体では、機体1よりも「緑のログ」の結末に到達しやすい。そしてそれこそが、危険である理由である。**

**ファームが答える。** `ping` は `yaw(id1)=ok pitch(id2)=ok` を返し、`status` は `raw pos yaw=266 pitch=753` を印字する。⇒ **機械から返ってくる数で埋まったログを、それでも「何かが動いたかどうか」を知らないまま作れてしまう。** ⛔ **そしてサーボ自身の応答も、証拠ではない。** 記録がそれを正確に書いている:

> `[ScsServo] id: 1 get zero pos: 455 from settings` は NVS から読んだだけで、**バス通信の証拠にはならない。** 動く証拠は、**「実際に首が動いたこと」だけである。**

⇒ **あちらと同じである: 緑のログが持てるのは、ホストから出たものと、電線から戻ってきたものである。そのどちらも「動いた」ではない。**

**何を書き残し、どこへ行くか。** ⚠️ **2つの別のものであり、行き先も2つである**——**機体1の頁と同じ規則である。**

| 何を | どこへ |
|---|---|
| **起きたことの全部を、順に**——どの MAC で、どのポート名で、何を焼き、**そして何かが動いたかどうか。** | **`projects/`**——記録の器。⛔ **空であり、その形は意図的に決まっていない**（`CLAUDE.md` を見よ）。 |
| **知見——いま文書が言っていることを変えるもの。** | ⚠️ **いま「不明」と言っている文書へ戻す**——`CLAUDE.md` の § Safety、機体1の頁、そしてこの頁。**戻さなかった知見は、文書を嘘のまま残す。** |

⛔ **そして `examples/` は存在しない。** **`projects/` が、仕事と記録の唯一の置き場である。**
