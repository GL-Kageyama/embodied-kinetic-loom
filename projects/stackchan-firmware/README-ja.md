# projects/stackchan-firmware/ — 電線の機体側

✅ **ビルドし、焼き、頭が回った——2026-10-18。** このディレクトリは `build/stackchan-vessel.bin` を作り、`0x510000` に書き、ハッシュで照合し、走らせた: アプリは `ready.` を印字し、両方のサーボが ping に答え、`bench move 5` が頭を回した。✅ **そして同じ日の後半、初めて、目標がホストから来た:** 20 ms ごとの `pose` 行が 678 本、拒否ゼロ、そして見ていた著者が「動いた」と言った。✅ **そのあと、12個の LED が点き、語に従った**——`warm` は橙に、`alert` は黄色に、`breathe` は呼吸になった——**インストール済みのデーモンが、伝送路を通り、コンソールを経て書いた語でも。** ✅ **そのあと、5つの身振りが測られ、名づけられ、枠から演じられた**——身振りはもう角度を発明する必要がなく、それを運ぶ枠は頭を動かす。⚠️ **5語は同じ日に著者の判断で改名された**: `look_up`、`look_side`、`nod`、`rest`、`recoil`。**記録は `records/2026-10-18-first-arrival.md`、`records/2026-10-18-the-lights.md`、`records/2026-10-18-the-gestures.md` であり、観察が3つとも背骨である。**

**ここに在るもの:** 1つのコマンド枠の読み手と、身振りの表——手元の個体で著者の目によって測られた5つの姿勢。**ここに無いもの:** 補間。⛔ **身振りは1つの速さの1回の移動と停止であり、著者の言葉では「動きが硬い」。** 滑らかさはエンジンの仕事であり、**エンジンはこの機体で一度も走っていない。**

⚠️ **この表は推測ではない。** どの数も、`bench set` で姿勢を置き、その語を頭が示しているかを著者に尋ねて得た（`records/2026-10-18-the-gestures.md`）。**当て推量の角度は、ソースの中では測定された角度と見分けがつかない**——だから測定の前に1つも書かなかったし、pitch の床に座る2つの姿勢はそう名乗っている。

## 枠が運ぶもの

**1コマンドにつき JSON 1行**、そしてコマンドは、機体の見せるものが変わったときだけ届く——段階・顔・光・選ばれた身振りのどれかであり、流れではない。⚠️ **首が動くのは遷移のときだけである**: 身振りはそこでだけ選ばれる。契約は `schemas/stackchan-command.schema.json` であり、両端がそれを読む。

| 欄 | 値 | 意味 |
|---|---|---|
| `face` | Pet の5つの顔、または `null` | この表情を出す。`null` = 変えない |
| `light` | `off` / `dim` / `breathe` / `warm` / `alert` / `error` | 常に在り、`null` にならない |
| `gesture` | `look_up` / `nod` / `look_side` / `rest` / `recoil`、または `null` | 首を動かす。`null` = 動かさない |

⛔ **`sound` の欄は無い。** スピーカーはまだ存在しないチャンネルである。

## ベンダーのソースが記録していること

✅ **2026-10-18 から、これらは記録に在る**——`m5stack/StackChan`、ブランチ `firmware-dev`、MIT。手元の個体に入っているファームである。⚠️ **これはベンダーの数であり、コードから読んだものであって、ここで測ったものではない。** このリポジトリはそれを読むが、所有はしない。

| 何 | ベンダーの記録 |
|---|---|
| サーボバス | UART1、1,000,000 baud、TX GPIO 6、RX GPIO 7。Feetech SCSCL |
| スケール | `raw = zero + angle × 16 / 5 / 10`、`angle` は 0.1° ⇒ **1カウントは 0.3125°**。逆は `(raw − zero) × 5 × 10 / 16` |
| yaw（ID 1） | 既定のゼロ 460、範囲 ±1280（0.1°）= **±128.0°**、raw 0–1000 |
| pitch（ID 2） | 既定のゼロ 620、範囲 30–870（0.1°）= **+3.0°〜+87.0°**、raw 0–1000、ストール保護あり |
| ゼロ点 | NVS、名前空間 `servo`、キー `zero_pos_1` / `zero_pos_2`——⚠️ **この個体の実測ゼロ点はここに在る** |
| LED | 12個。PY32 IO エキスパンダ（I²C `0x6F`、SDA GPIO 12、SCL GPIO 11）の先。同じエキスパンダが **サーボ電源** をピン0で切る |

✅ **2026-10-18 から角度は在る**——この個体で測られた5つの姿勢である（`records/2026-10-18-the-gestures.md`）。表は `main/main.cpp` にあり、どの数がどこから来たかを言う注の隣にある。

| 身振り | yaw | pitch | 何をするか |
|---|---|---|---|
| `look_up` | +8.0° | 50.0° | 顔が上がる |
| `look_side` | +35.0° | 50.0° | 顔が横へ向く |
| `rest` | 0.0° | 3.0° | 顔が下がり、そこに居る |
| `nod` | +8.0° | 50.0° → 3.0° → 50.0° | 下ろして戻る |
| `recoil` | −8.0° | 70.0° | 顔が引いて上を向く |

⛔ **`rest` と `nod` の下ろし先は、機体の pitch の床に座っている**——3.0°、ベンダーの下限である。もっと低い語は、ここでは低くなれない。

⛔ **これらは姿勢であって、軌道ではない。** 各身振りは、サーボ自身の速さの欄による1回の移動と、そのあとの停止である。**何も補間しない。**

## サーボの time フィールドが答えたこと — 2026-10-18

✅ **`bench timed <yaw_deg> <time> [speed]` をベンチに足し、同じ日に焼いた。** これは**1回だけ**目標を書く——time フィールドと speed フィールドを伴って——`bench move` が1秒ごとに目標を書き直すのとは違う——**そのあと200 ms ごとに、最大70秒、yaw の軸を読む。**

⛔ **この機体では、time フィールドは移動時間を決めなかった。決めたのは speed フィールドである。** 2回の試行: `time=5000, speed=0` は5カウント動いて止まり、`time=500, speed=100` は32カウント（10°）を約0.3〜0.4秒で、約127カウント/秒で動いた。**どちらも目標のちょうど6カウント手前で止まった**——見たところ固定のずれであり、バックラッシュとも読み戻しそのものとも、まだ分けていない。

⇒ **エンジンにとっての意味を1行で: この機体では、滑らかさをサーボに任せることはできない。** 段差のない首は、**ホストが補間した目標を書き続ける**ことを要る——`engine/trajectory/` はそのために在り、**そしてそれはこの機体では一度も走っていない。** ⚠️ **数字は `records/2026-10-18-first-arrival.md` にあり、そこでは数字が伴っていた観察が背骨である。**

## 姿勢の行、そして基板がそれを読む——2026-10-18

✅ **`pose <yaw_tenths> <pitch_tenths>*<CC>` の基板側が `main/main.cpp` に在る。** 最初の語で振り分けられ、**ホストの符号器が前提しているとおり**であり、5つのことをする:

| 何を | どう | 
|---|---|
| 長さ | **64** バイトを超えたら `pose: refused (too-long)` |
| チェックサム | 最後の `*` の後の2桁の16進が、それ以前の総和 `& 0xFF` と一致すること |
| 欄 | 空白はちょうど1つ、**両方が Python の復号器と同じ綴り規則で読まれる**——`05`、`-0`、`+5` はすべて拒否 |
| clamp | **この機体の**限界（`board::kYawAngleLimitTenths`、`kPitchAngleMin/MaxTenths`）に対して。プロトコルの限界ではない |
| 最初の行 | 両方の目標を現在位置に置き、トルクを入れ、200 ms——**最初の姿勢が跳びではなく移動になるように** |

⛔ **拒否は、ストリームごとにコード1つにつき1回だけ印字する。** 50 Hz で拒否ごとに印字すれば、**いちばん大事な1行を埋めてしまう**——`pose: stream lost after 500 ms — torque released`。

⚠️ **ウォッチドッグはコンソールのタスクではなく、メインループで走る**——コンソールのタスクは `read()` で止まるからである。**それで1本の UART に2つのタスクが載ったので、`servo.cpp` はバスの周りにミューテックスを持つ**——⛔ **混ざったパケットは、拒否された命令ではない。別の命令か、沈黙である。**

✅ **同じ日に測った、±5° の6往復:** 678 の姿勢、**拒否ゼロ、clamp ゼロ**、ウォッチドッグは往復ごとに1回鳴った。**pitch は `857` の十分の一度で命令し、前も後も 894 と読めた**——印字された 85.6° ではない（それは 893 に戻る）。⚠️ **どの往復も、中心より約6カウント下で終わった**——timed のベンチと同じ不足である。

⛔ **これが意味しないこと: エンジンが走った、ではない。** 補間はこのリポジトリの外のホスト道具（`~/stackchan/pose_stream.py`）にあり、`engine/trajectory/` にはない。**`Motion Intent` は読まれず、伝送路は今も選ばれていない。** **記録は `records/2026-10-18-first-arrival.md`。**

⚠️ **ストリームが走っている間、`bench` は拒まれる**（`bench: refused — a pose stream is running; wait for 500 ms of silence`）——`bench` はコンソールを数秒ふさぎ、**遅れて届いた姿勢は、姿勢ではない**からである。

## 光 — 2026-10-18

✅ **12個の LED は動き、デーモンからの枠がそこへ届く。** ⛔ **同じ日の早い時間には動いていなかった**——基板が受理した枠が「光っていない」を生み、一方でエキスパンダのレジスタは正しい色を保持していた。**記録は `records/2026-10-18-the-lights.md` であり、観察がその背骨である。**

| light | 色（RGB565 の源） | どこで選ばれたか |
|---|---|---|
| `off` | `{0, 0, 0}` | `main/leds.cpp` |
| `dim` | `{24, 24, 40}` | `main/leds.cpp` |
| `breathe` | `{40, 48, 72}`、3秒かけて 20%〜100% を往復する三角波 | `main/leds.cpp` |
| `warm` | `{112, 64, 24}` | `main/leds.cpp` |
| `alert` | `{160, 104, 0}` | `main/leds.cpp` |
| `error` | `{144, 0, 0}` | `main/leds.cpp` |

⛔ **そのどれも測定ではない。** 12個は I²C `0x6F` の PY32 IO エキスパンダの先へ書かれる: `0x24` の `LED_CFG` が個数をビット0〜5に、refresh をビット6に持ち、ピクセルは `0x30` から RGB565 のリトルエンディアンである。

✅ **`bench leds` は、1つの問いを2つにするために足された。** エキスパンダを読み戻す——バージョン、`LED_CFG`、データ線の先の6つのレジスタ、最初の4ピクセル——そして12個すべてに赤を書き、ピクセル0をもう一度読む。**「レジスタが値を受けた」と「ピクセルが点いている」を別々に問い、どちらの答えも印字する。**

⚠️ **結果を変えたものは1つであり、それは仮説である:** エキスパンダが電源断で初期化し直された。基板はハングからの回復のために抜かれ、戻された後に、**新しいコード無しで**12個が点いた。⛔ **ここでは電源断を、挿したこと、再列挙、直前にあった焼き直しから切り分けていない。**

### この基板での2度のハング

⛔ **`LED_CFG` のビット7——ベンダーのどのドライバも書かないビット——を書いたベンチ命令が、コンソールとハートビートと USB-Serial-JTAG の ROM を止めた。USB デバイスは列挙されたままだった。** 回復したのは抜き差しだけであり、命令は削除され、理由は `main/leds.cpp` に残っている: **触られていないレジスタビットは「未使用」ではなく「未知」である。**

⛔ **2度目のハングは、電線ではなく読み取り手から来た。** `pyserial` の open が基板をリセットし（`rst:0x15 (USB_UART_CHIP_RESET)`）、読み取り側は起動の途中で流れを失い、ROM は答えなくなった。**デーモン自身の経路——`os.open`、`os.write`、`os.close`、枠ごとに1回——はその後、単独で走り、何もリセットしなかった。** コンソールは `os.open` と生の `termios` で読んだ。⚠️ **DTR と RTS を立てる読み取り手は、この機体を再起動している。**

### 2人ではなく1人の行為者

⚠️ **この個体は、`ota_1` のアプリを置き換え得るベンダーのアプリを `ota_0` に載せて出荷された。** 一度、`otadata` を消してそれを起動すると、ネットワークへ繋ぎ、このリポジトリのスロットへの OTA を始めた。⇒ **ベンダーのイメージを基板から読み出し（5,177,344 バイト、SHA-256 `97b176…cf64ab5b`、このリポジトリの外 `~/stackchan/vendor-image/` に保管）、それから `ota_0` を消した**（`erase-region 0x20000 0x4f0000`、4.9 秒）。⛔ **そのファイルが唯一の写しであり、どの検査も覆っていない。**

⚠️ **そしてコンソールの経路は身元ではない。** ハングの前は `/dev/cu.usbmodem1101`、1度の抜き差しの後は `/dev/cu.usbmodem101` だった——**16分違い、同じ基板。** インストール済みの plist は2つ目を名指ししている。次の抜き差しは3つ目を名指しするかもしれず、**無い経路へ書かれた枠は `sent: false` として記録され、投げられない。**
