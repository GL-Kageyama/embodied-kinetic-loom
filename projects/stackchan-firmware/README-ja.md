✅ **ビルドし、焼き、頭が回った——2026-10-18。** このディレクトリは `build/stackchan-vessel.bin` を作り、`0x510000` に書き、ハッシュで照合し、走らせた: アプリは `ready.` を印字し、両方のサーボが ping に答え、`bench move 5` が頭を回した。✅ **そして同じ日の後半、初めて、目標がホストから来た:** 20 ms ごとの `pose` 行が 678 本、拒否ゼロ、そして見ていた著者が「動いた」と言った。✅ **そのあと、12個の LED が点き、語に従った**——`warm` は橙に、`alert` は黄色に、`breathe` は呼吸になった——**インストール済みのデーモンが、伝送路を通り、コンソールを経て書いた語でも。** ✅ **そのあと、画面が vendor 自身の顔を描いた**——まぶた付きの白い円盤2つと口の棒、アンチエイリアス付きで、枠の `face` 欄から。✅ **そのあと、5つの身振りが測られ、名づけられ、枠から演じられた**——身振りはもう角度を発明する必要がなく、それを運ぶ枠は頭を動かす。⚠️ **5語は同じ日に著者の判断で改名された**: `look_up`、`look_side`、`nod`、`rest`、`recoil`。**記録は `records/2026-10-18-first-arrival.md`、`records/2026-10-18-the-lights.md`、`records/2026-10-18-the-gestures.md` であり、観察が3つとも背骨である。**

**ここに在るもの:** 1つのコマンド枠の読み手と、身振りの表——手元の個体で著者の目によって測られた5つの姿勢。**ここに無いもの:** 補間。⛔ **表から演じる身振りは1つの速さの1回の移動と停止であり、著者の言葉では「動きが硬い」。** 滑らかさはエンジンの仕事であり、✅ **0.19.10 からエンジンがこの機体を駆動した**: `projects/stackchan/neck/` が `engine/trajectory` の標本を 20 ms の `pose` の行として流した——7つの区間、822が適用され、拒否ゼロ、clamp ゼロ。⛔ **そして 0.19.11 から、姿勢の流れは純正ファームウェアが書くものを書く**——`WritePos(id, angle, 20, 0)`——古い呼び出し（`time=0, speed=100`）は**こちらの掛けた40°/s の減速であり、サーボの天井ではなかった**からである。**この個体で、同じ目標を1つずつ: 純正の呼び出しなら112カウント（35°）を200 ms 未満、こちらなら約1.0秒。** ✅ **同じ7区間を1/3の長さで流した: 228姿勢、基板で410が適用、拒否0、clamp 0——著者の判定は「かなり良い。これでOKだと思う。」** ⚠️ **記録は `records/2026-10-18-the-neck.md`。**

⚠️ **この表は推測ではない。** どの数も、`bench set` で姿勢を置き、その語を頭が示しているかを著者に尋ねて得た（`records/2026-10-18-the-gestures.md`）。**当て推量の角度は、ソースの中では測定された角度と見分けがつかない**——だから測定の前に1つも書かなかったし、pitch の床に座る2つの姿勢はそう名乗っている。

## 枠が運ぶもの

**1コマンドにつき JSON 1行**、そしてコマンドは、機体の見せるものが変わったときだけ届く——段階・顔・光・選ばれた身振り・そして言うべき語のどれかであり、流れではない。⚠️ **首が動くのは遷移のときだけである**: 身振りはそこでだけ選ばれる。契約は `schemas/stackchan-command.schema.json` であり、両端がそれを読む。

| 欄 | 値 | 意味 |
|---|---|---|
| `face` | Pet の5つの顔、または `null` | この表情を出す。`null` = 変えない |
| `light` | `off` / `dim` / `writing` / `busy` / `breathe` / `warm` / `alert` / `error` | 常に在り、`null` にならない |
| `gesture` | `look_up` / `nod` / `look_side` / `rest` / `recoil`、または `null` | 首を動かす。`null` = 動かさない |
| `sound` | `hello` / `pip` / `chime` / `fall`、または `null` | この語を鳴らす。`null` = この枠は黙る |

⚠️ **`sound` は、状態ではなく事象である唯一の欄である**: `null` は*最後の語を保て*ではなく、*何も言うな*を意味する。⛔ **基板は4つの語を知っていて、いつが正しいかは何も知らない**——それを決めるのはホストであり、写像は `projects/stackchan/behaviors.py` である。

## ベンダーのソースが記録していること

✅ **2026-10-18 から、これらは記録に在る**——`m5stack/StackChan`、ブランチ `firmware-dev`、MIT。手元の個体に入っているファームである。⚠️ **これはベンダーの数であり、コードから読んだものであって、ここで測ったものではない。** このリポジトリはそれを読むが、所有はしない。

| 何 | ベンダーの記録 |
|---|---|
| サーボバス | UART1、1,000,000 baud、TX GPIO 6、RX GPIO 7。Feetech SCSCL |
| スケール | `raw = zero + angle × 16 / 5 / 10`、`angle` は 0.1° ⇒ **1カウントは 0.3125°**。逆は `(raw − zero) × 5 × 10 / 16` |
| yaw（ID 1） | 既定のゼロ 460、範囲 ±1280（0.1°）= **±128.0°**、raw 0–1000 |
| pitch（ID 2） | 既定のゼロ 620、範囲 30–870（0.1°）= **+3.0°〜+87.0°**、raw 0–1000、ストール保護あり |
| ゼロ点 | NVS、名前空間 `servo`、キー `zero_pos_1` / `zero_pos_2`——⚠️ **この個体の実測ゼロ点はここに在る** |
| LED | 12個。PY32 IO エキスパンダ（I²C `0x6F`、SDA GPIO 12、SCL GPIO 11）の先。同じエキスパンダが **サーボ電源** をピン0で切る |

✅ **2026-10-18 から角度は在る**——この個体で測られた5つの姿勢である（`records/2026-10-18-the-gestures.md`）。表は `main/main.cpp` にあり、どの数がどこから来たかを言う注の隣にある。

| 身振り | yaw | pitch | 何をするか |
|---|---|---|---|
| `look_up` | +8.0° | 50.0° | 顔が上がる |
| `look_side` | +35.0° | 50.0° | 顔が横へ向く |
| `rest` | 0.0° | 3.0° | 顔が下がり、そこに居る |
| `nod` | +8.0° | 50.0° → 3.0° → 50.0° | 下ろして戻る |
| `recoil` | −8.0° | 70.0° | 顔が引いて上を向く |

⛔ **`rest` と `nod` の下ろし先は、機体の pitch の床に座っている**——3.0°、ベンダーの下限である。もっと低い語は、ここでは低くなれない。

⛔ **これらは姿勢であって、軌道ではない。** 各身振りは、サーボ自身の速さの欄による1回の移動と、そのあとの停止である。**何も補間しない。**

## サーボの time フィールドが答えたこと — 2026-10-18

✅ **`bench timed <yaw_deg> <time> [speed]` をベンチに足し、同じ日に焼いた。** これは**1回だけ**目標を書く——time フィールドと speed フィールドを伴って——`bench move` が1秒ごとに目標を書き直すのとは違う——**そのあと200 ms ごとに、最大70秒、yaw の軸を読む。**

⚠️ **この機体では、`time` がゼロなら speed フィールドが決め、`time` がゼロでなければ time フィールドが決める**——2026-10-18 の2回の試行は、それぞれ片方の欄だけを変えた: `time=20, speed=0` は112カウント（35°）を200 ms 未満で動き、`time=0, speed=100` は同じ112カウントを約1.0秒で動いた。⛔ **以前の対は両方の欄を同時に変えていた**（`time=5000, speed=0`: 5カウントで停止; `time=500, speed=100`: 32カウントを約0.3〜0.4秒）——**だから両者を分けられない。あの読みは確認ではなく、置き換えられた。** **どの試行も目標の6〜8カウント手前で止まった**——見たところ固定のずれであり、バックラッシュとも読み戻しそのものとも、まだ分けていない。

## 姿勢の行、そして基板がそれを読む——2026-10-18

✅ **`pose <yaw_tenths> <pitch_tenths>*<CC>` の基板側が `main/main.cpp` に在る。** 最初の語で振り分けられ、**ホストの符号器が前提しているとおり**であり、5つのことをする:

| 何を | どう | 
|---|---|
| 長さ | **64** バイトを超えたら `pose: refused (too-long)` |
| チェックサム | 最後の `*` の後の2桁の16進が、それ以前の総和 `& 0xFF` と一致すること |
| 欄 | 空白はちょうど1つ、**両方が Python の復号器と同じ綴り規則で読まれる**——`05`、`-0`、`+5` はすべて拒否 |
| clamp | **この機体の**限界（`board::kYawAngleLimitTenths`、`kPitchAngleMin/MaxTenths`）に対して。プロトコルの限界ではない |
| 最初の行 | 両方の目標を現在位置に置き、トルクを入れ、200 ms——**最初の姿勢が跳びではなく移動になるように** |

⛔ **拒否は、ストリームごとにコード1つにつき1回だけ印字する。** 50 Hz で拒否ごとに印字すれば、**いちばん大事な1行を埋めてしまう**——`pose: stream lost after 500 ms — torque released`。

⚠️ **ウォッチドッグはコンソールのタスクではなく、メインループで走る**——コンソールのタスクは `read()` で止まるからである。**それで1本の UART に2つのタスクが載ったので、`servo.cpp` はバスの周りにミューテックスを持つ**——⛔ **混ざったパケットは、拒否された命令ではない。別の命令か、沈黙である。**

✅ **同じ日に測った、±5° の6往復:** 678 の姿勢、**拒否ゼロ、clamp ゼロ**、ウォッチドッグは往復ごとに1回鳴った。**pitch は `857` の十分の一度で命令し、前も後も 894 と読めた**——印字された 85.6° ではない（それは 893 に戻る）。⚠️ **どの往復も、中心より約6カウント下で終わった**——timed のベンチと同じ不足である。

⛔ **これが意味しないこと: エンジンが走った、ではない。** 補間はこのリポジトリの外のホスト道具（`~/stackchan/pose_stream.py`）にあり、`engine/trajectory/` にはない。**`Motion Intent` は読まれず、伝送路は今も選ばれていない。** **記録は `records/2026-10-18-first-arrival.md`。**

⚠️ **ストリームが走っている間、`bench` は拒まれる**（`bench: refused — a pose stream is running; wait for 500 ms of silence`）——`bench` はコンソールを数秒ふさぎ、**遅れて届いた姿勢は、姿勢ではない**からである。

⛔ **この日まで、`bench power on` は展開器が書をどう扱ったかにかかわらず ON と印字していた。** コマンドは書が落ちたかを一度も尋ねていない——**印字は主張であり、答えではなかった。** ⇒ **今は `leds::servo_power()` の戻り値を検査し**、`the expander took the write` か `THE EXPANDER DID NOT TAKE THE WRITE` を印字し、そのあと `servo_power_probe()` を呼ぶ。

**探針が読むもの**、ピン0、サーボのレールの有効線:

|---|---|---|
| `M_L` `0x03` | `0x01` | ピン0は出力 |
| `O_L` `0x05` | `0x01` | 出力は高い |

### スイッチは、レール自身の電源だった——2026-10-19

⛔ **残る問いは物理であり、その最初のものは電源を切ることで答えた。** `bench power off`、3秒、`bench power on`、そして `bench scan`: **2 id(s) が答えた。** ⇒ **レールも、スイッチも、VM の経路も、展開器のピンも、配線も、原因ではなかった。**（電源スイッチの問いは、著者が外から先に閉じていた: USB を抜いても画面は点いたまま——**機体は電池で走る。**）

✅ **同じ日に `bench state <id>` を足した**——56〜63 を一度に読み、SCSCL の表では位置・速度・負荷・電圧・温度である。バスが戻った瞬間:

| id | raw | 電圧 | °C | 負荷 | status |
|---|---|---|---|---|---|
| 1 | 469 | **5.1 V** | 32 | 0 | `0x00` |
| 2 | 776 | **5.1 V** | 31 | 0 | `0x00` |

⚠️ **この電圧はサーボ自身の読みであり、テスタの値ではない**——**サーボから見たレールである。** ⛔ **電流や負荷経路の測定ではなく、暗いサーボは何も言わない。**

⛔ **つまり沈黙は、サーボが抱える状態である。** このチップのリセットをまたいで残る——DTR/RTS のパルスでボードを再起動してもバスは黙ったままで、晴らすのはサーボの電源を切ることだけである。続く有界の `bench move 0 60` で首は動き（ヨー 474→460、ピッチ 767→812）、**その動きのあとバスはまた黙った**；もう一度のレールの電源サイクルが戻した。

✅ **0.19.31 から `app_main` がレールのスイッチを自分で投げる**——バスが上がる前に: `servo_power(false)`、`servo_power(true)`、それから `scs::begin()`。⚠️ **その早さではトルクが無いので、これで何かが動くことはない**——だが、チップがリセットした瞬間に保持されていた頭は、レールが落ちているあいだ垂れる。⛔ **0.19.34 まではその切断が 300 ms だった**——選ばれただけで一度も測られていない数である。**いまは測られた3秒である。**

⚠️ **同じ日に `bench raw <id>` を足した**——`read_position` は非ゼロのステータスバイトを「無応答」と呼ぶので、**拒んでいるサーボと居ないサーボが同じ言葉だった。** これは1バイトずつ印字し、ステータスをビットで名指し、何も拒まない。

⛔ **まだ答えていないこと**: 何がサーボをその状態に置くのか。有界の動きのあとに一度起きたが、他の多くの時間には起きていない——**引き金はまだ名指されていない。そして起動時にレールを回すのは診断ではなく回復である。**

### 基板がバスを見張る——2026-10-19

⚠️ **3度目の沈黙はホストのログの中で見つかり、その背後に窓を残した。** 位置を運んだ最後の読み戻しは `at=17537.504` の `[100, 487]`、何にも当たらなかったことが確かな最初の探針は `at=18906.163`——**1,368.7秒、およそ22.8分**であり、その区間に**身振りは送られておらず、再起動も無い。** ⇒ **バスは、何も尋ねられていないあいだにも自分で黙る。**

⛔ **そこで7つの形をコマンドで試したが、7つとも答えられた**: 時間欄つきの45°動作を200 msごとに70秒読み、50ポーズの流し、`bench sound hello`、枠→78ポーズの流し、デーモンの順序（探針・流し・枠）、流しの**途中で**別の fd から枠、そして24の身振り連打。

⇒ **`ServoWatchdog()` がメインループで走る**——ポーズの監視と並び、理由も同じである：**コンソールのタスクは `read()` で止まるので、自分が居ない沈黙には気づけない。** 待機中は両方の id を **5秒**ごとに ping し、**3連続の沈黙**を状態とみなし、レールを測られた **3秒**落とす；そして現在位置を目標に書き戻し、トルクを落とす——**手で `bench power on` したときと同じ後始末である。**

✅ **手を離して測った**: コンソールに `bench power off` と打つと、基板はこう言った

```
servo: no answer (1 of 3 before the rail is cycled)
servo: no answer (2 of 3 before the rail is cycled)
servo: silent for 3 checks — cycling the rail (1 since this boot)
servo: rail cycled — ping yaw=0/3 pitch=3/3
servo: present yaw=496 pitch=777; goals set; torque off
```

——最初の打撃は **0.5秒**、2回目は **5.5秒**、巡回は **10.5秒**、バスが戻ったのは **15.0秒**、位置が読めたのは **15.2秒**。⇒ **レールを切ったところから、バスが答えるまでおよそ15秒。** ⚠️ **ヨーのサーボは通電が戻って0.3秒後の3回の ping を外し、次の試みで 496 を読んだ**——2つの軸は同じ瞬間には起き上がらず、1時点の ping の1回の数えは、その隙間がどれだけ長いかを言えない。⛔ **これは回復であり、診断ではない**；**1回の ping の失敗もほかの沈黙と同じように数えられる**——健全なバスでそれがどれだけ失敗するかは測っていない。記録は `records/2026-10-19-the-machine-recovers-itself.md` である。

### 監視とコンソールは、同じバスを欲しがった — 2026-10-19

⛔ **監視は前日に書かれ、使われた最初の日に、答えているバスを沈黙と数えた。** `bench move` は遅い目標送りである：`MoveAxis` は目標を3カウント書き、1秒待ち、位置を読む——**動きが続くかぎり、1秒に一度**。45°なら138カウント、およそ46秒である。

⇒ **半二重のバスに2人の読み手が居れば、互いの返事を取る。** bench の刻みは位置を印字し続け、そのあいだ監視は自分の ping が答えられなかったと数えた——**その規則では3連続が状態である**——そして**1回の起動で6回**レールを投げた。そのすべてが bench の命令の最中だった。⚠️ **6つのうち2つは行を読んで確かめ、残りは基板自身のカウンタが名指す。**

✅ **0.19.35 から、コンソールはバスを使っていることを監視に告げる**：`ConsoleTask` が `Dispatch()` を呼ぶ前後で `g_console_busy` を立て下げし、`ServoWatchdog()` はそれが立っているあいだ降りる。**読み手は同時に1人**——そして監視が書かれた理由の規則は変わっていない：**誰も起こしていない沈黙は、いまも気づかれ、取り除かれ、印字される。**

✅ **変更後に測った**: `bench move 80`（この台の45°にクランプ）は **46秒**、監視の5秒の窓でおよそ**9つ**動き、**`no answer` もレール巡回も0**だった。変更前は同じ形が15秒以内に巡回した。

⚠️ **`bench move` は頭ではなく目標を進める。** `MoveAxis` は戻る前に読み返さず、トルクはすぐ落ちる：目標は **604**、手を離したときの頭は **592** だった。**12カウントはサーボの遅れであり、失われた命令ではない。**

⛔ **長く続いた「答えない」の答えは、コンソール自身の門である**：流しの最中に `bench pos` を尋ねると

```
bench: refused — a pose stream is running; wait for 500 ms of silence
```

と印字する——idle の `bench pos` はおよそ0.3秒で答える。**デーモンの探針は自分の流しの前に走るので、この門に当たらない**；詰まったように見えたコンソールは、断っていた基板であり、断りは印字されていた。

✅ **そして読み戻しの最初の使い道は、身振りの測定だった**——`docs/stackchan-progress.md` の7段目：設置済みデーモンを通して、`look_up` は首を **0カウント**、`look_side` は **71** 動かした。⛔ **`main.cpp` はどの検査にもコンパイルされない**；確かめるのは `idf.py build` と、基板自身の印字である。

## ラジオ — 2026-10-21

⛔ **`main/wifi.cpp` はステーションを立ち上げ、そして何も運ばない。** 枠も pose もその上を通らず、既存の挙動は一つも変わっていない。足したのは bench の動詞3つと、起動バナーの1行である:

```
bench wifi                        NVS の資格情報・関連付け・アドレス
bench wifi scan                   SSID・チャネル・RSSI・認証方式——数秒ブロックする
bench wifi join <ssid> [psk]      網を保存して接続する；⛔ psk は印字されない
reset: reason <n> (<name>)        起動バナーの新しい行
```

⚠️ **ここが報告する資格情報はベンダーのものである**: `esp_wifi_get_config` は設定ウィザードが NVS に書いたものを読む。このファイルは、`join` が打たれない限り、その塊を消しもしなければ書き換えもしない。⛔ **ここは PSK を印字しない**——長さでも、形でも。

⛔ **これが在るのは、コンソールが一本の線であり、2026-10-21 にホストがその線を二度奪ったからである** — `terminateDevice … hardware port disabled` が `03:24:03.560` に、そして `03:48:01.891` に、**基板が答えた差し直しの 70.7 秒後に。** 記録は `records/2026-10-21-the-board-that-would-not-answer.md` である。

⚠️ **`reset: reason` の行は、一つの問いを決めるためだけに在り、それ以外の何も決めない**: ケーブルの差し直しがこのチップの電源を入れ直すかどうか、である。入れ直すなら、70.7 秒は**冷えた起動のたびに再現する故障の長さ**であり、入れ直さないなら、**一つの状態が二度ポートを終わらせた。** ⛔ **起動の行は、起きなかった起動を書けない**——だからここに印字されるものは、チップが一度も再起動しなかった場合を覆わない。

✅ **2026-10-21、ラジオはそれが問うために作られた問いに答えた——そしてその答えは起動ループを1つ払った。** ステーションは繋がる: `wifi: connected ip=192.168.0.19`、`ch 1 rssi -60`、WPA2-PSK、ベンダーのウィザードが既に保存していたネットワーク上で。⛔ **その一行が印字される前に、どの起動もアドレスが来ておよそ1秒後に死んでいた**——`LoadProhibited`、キューへのポインタからの `l32i` で、そのフィールドには PS レジスタの値が入っていた。**終端を越えてヒープへ走ったスタックは、そう見える。** **コアダンプがそれを名指しした**: タスクは `sys_evt`、割り込まれた先は `esp_netif_lwip_ipc_call_get_netif`——`IP_EVENT_STA_GOT_IP` のハンドラが呼んでいた `esp_netif_get_ip_info` の裏の IPC 往復である——そしてスタックは自分の領域を出ていた。このタスクのスタックは `CONFIG_ESP_SYSTEM_EVENT_TASK_STACK_SIZE`、**既定 2304**。⇒ **4096 では、ハンドラは `sys_evt stack, 1600 bytes never used` と報告する**。つまり必要量は約 2,496——**既定をおよそ 200 バイト超えている。** ⚠️ **ハンドラはもうその呼び出しをしない**——イベントがアドレスを運んでおり、ペイロードから読めば2つ目のタスクのフレームを払わずに済む——**それでもスタックも上げた。測定が言っているのは、欠陥が呼び出しではなく余裕のほうだった、ということだからである。** ⚠️ **この設定は `sdkconfig.defaults` にあり、`sdkconfig` には無い**: 生成されるファイルは gitignore されているので、そこにだけ書かれた修正はきれいな checkout で消える。`sdkconfig` を消し、再構成し、4つの値を読み戻して確かめた。

⚠️ **`main/net.cpp` は経路の探針であって、体の機能ではない。** 3333 にリスナーを、同じ番号に UDP の耳を開き、相手を印字し、行には**その長さだけ**を答える——⛔ **決してディスパッチしない。** コンソールが既に体を持っており、1本の半二重バスに2人目の書き手を置くことが 0.19.27 の測った失敗だからである。`bench net call <ip> <port> <text>` は外へ接続を1本開き、戻ってきたものを読む。どれも枠も pose も運ばない。

⛔ **そして経路は非対称であり、それがその日の発見のすべてである。** Mac からこの基板へは、**何ひとつ届かなかった**: 33回の `connect()` はすべて `EHOSTUNREACH`、**1回 0.1 ミリ秒**; `en0` に束縛しても同じ; 試したどのポートの UDP でも同じ; サブネットブロードキャストでも同じ; そして枠が途中で到着する9秒間に87回試して——**開いたのは 0回、基板は `0 datagram(s)` と数えた**。⚠️ **その拒否はホストのものである**: 枠が出て戻ってくるより前に返り、しかも `route get` が新しい項目（`expire 1182`）を、`arp -an` がこの基板自身の MAC を持っているあいだに返った——本当に居ないホストは `(incomplete)` と出た。**同じ束縛ソケットでの対照**: ゲートウェイの 80 は 0.005 秒で開き、53 は 17 バイトで答えた。**基板に新しいアドレスを与えても拒否された**ので、1つの古い項目の問題ではない; **無償 ARP も何も変えなかった。** 逆向きは**毎回通った**: UDP を1つ外へ出せば答えが戻り（`net: reply "pong"`）、**基板が開いた TCP 接続は両方向を運んだ**——Mac が行を読んで答え、基板は `net: the host said "yes-loud-and-clear"` と印字した。⇒ **証明された向きは外である。** ⛔ **Mac がなぜ拒むのかは分かっていない**: パケットキャプチャは取っておらず（root が要る）、**この基板**と**どの無線クライアントでも**を分ける2台目も無かった。記録は `records/2026-10-21-two-directions.md` である。

⚠️ **値段は 517,808 バイトである** — ラジオの前が 357,520、後が 875,328。Wi-Fi のスタック全体（`esp_wifi`・`lwip`・`wpa_supplicant`・`mbedtls`）は、コードが初めてその名前を出した時点でリンクされる。アプリのパーティションは 5.1 MB で、その 83% がまだ空いている。
