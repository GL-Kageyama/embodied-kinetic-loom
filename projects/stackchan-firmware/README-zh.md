## 帧携带什么

**每条命令一行 JSON**，而命令在机体该显示的东西发生变化时到达——阶段、脸、光、选中的身势，或一个要说的词；这不是流。⚠️ **脖子只在阶段转换时动**: 身势只在那里被选中。契约是 `schemas/stackchan-command.schema.json`，两端都读它。

| 栏 | 值 | 含义 |
|---|---|---|
| `face` | Pet 的五张脸，或 `null` | 显示这个表情。`null` = 不改变 |
| `light` | `off` / `dim` / `breathe` / `warm` / `alert` / `error` | 始终存在，永不为 `null` |
| `gesture` | `look_up` / `nod` / `look_side` / `rest` / `recoil`，或 `null` | 动脖子。`null` = 不动 |
| `sound` | `hello` / `pip` / `chime` / `fall`，或 `null` | 播放这个词。`null` = 这一帧沉默 |

⚠️ **`sound` 是唯一一个属于事件而不属于状态的栏位**: `null` 不是*保持最后一个词*，而是*什么也不说*。⛔ **板子知道四个词，却对何时正确一无所知**——那由主机决定，映射在 `projects/stackchan/behaviors.py`。

| 舵机总线 | UART1，1,000,000 baud，TX GPIO 6，RX GPIO 7。Feetech SCSCL |
| 标度 | `raw = zero + angle × 16 / 5 / 10`，`angle` 以 0.1° 计 ⇒ **一个计数是 0.3125°**。逆式 `(raw − zero) × 5 × 10 / 16` |

| pitch（ID 2） | 默认零点 620，范围 30–870（0.1°）= **+3.0°〜+87.0°**，raw 0–1000，带堵转保护 |

| 身势 | yaw | pitch | 它做什么 |
|---|---|---|---|
| `look_up` | +8.0° | 50.0° | 脸抬起来 |
| `look_side` | +35.0° | 50.0° | 脸转向一侧 |
| `rest` | 0.0° | 3.0° | 脸低下去，留在那里 |
| `nod` | +8.0° | 50.0° → 3.0° → 50.0° | 下去再回来 |
| `recoil` | −8.0° | 70.0° | 脸缩回去并抬起 |

⛔ **`rest` 和 `nod` 的下放点坐在机器的 pitch 地板上**——3.0°，厂商的下限。想更低的词，在这里低不下去。

⛔ **这些是姿态，不是轨迹。** 每个身势都是舵机自身速度栏的一次移动，然后停止。**什么都不插值。**

## 舵机的 time 字段回答了什么 — 2026-10-18

✅ **`bench timed <yaw_deg> <time> [speed]` 被加进台架，并在同一天烧入。** 它**只写一次**目标——带着 time 字段和 speed 字段——与每秒重写目标的 `bench move` 不同——**然后每 200 ms 读一次 yaw 轴，最多 70 秒。**

⚠️ **在这台机器上，`time` 为零时由 speed 字段决定，`time` 不为零时由 time 字段决定**——2026-10-18 的两次试次各自只改了一个字段：`time=20, speed=0` 把 112 个计数（35°）在 200 ms 以内运到，`time=0, speed=100` 把同样的 112 个计数用了约 1.0 秒。⛔ **早先的一对同时改了两个字段**（`time=5000, speed=0`: 走 5 个计数停住；`time=500, speed=100`: 约 0.3–0.4 秒走 32 个计数）——**所以它分不开两者；那个读法已被取代，而不是被确认。** **每一次试次都停在距目标 6 到 8 个计数处**——看上去是固定的偏移，与间隙、与回读本身都还没有分开。

⇒ **对引擎的意义，一行：在这台机器上，柔和不能委托给舵机。** 没有台阶的脖子，**需要主机持续写插值后的目标**——`engine/trajectory/` 正是为此而在，**而在那个时候，它在这台机器上从未跑过。** ✅ **自 0.19.10 起它跑过了；而自 0.19.11 起，决定可跟随运动大小的是舵机自身的天花板——约 175°/s**（见上）。⚠️ **数字在 `records/2026-10-18-first-arrival.md` 里，那里作为背骨的是伴随数字的观察；脖子自己的记录是 `records/2026-10-18-the-neck.md`。**

## 姿势那一行，而基板读它——2026-10-18

✅ **`pose <yaw_tenths> <pitch_tenths>*<CC>` 的基板端在 `main/main.cpp` 里。** 靠第一个词分发，**正是主机编码器所假设的那样**，它做五件事:

| 什么 | 怎么做 |
|---|---|
| 长度 | 超过 **64** 字节 → `pose: refused (too-long)` |
| 校验和 | 最后一个 `*` 之后两位十六进制，必须等于它之前全部字节的和 `& 0xFF` |
| 字段 | 恰好一个空格，**两栏都按与 Python 解码器相同的拼写规则解析**——`05`、`-0`、`+5` 全部拒绝 |
| clamp | 对着**这台机器**的界限（`board::kYawAngleLimitTenths`、`kPitchAngleMin/MaxTenths`），而不是协议的界限 |
| 第一行 | 把两个目标都设成当前位置、开扭矩、等 200 ms——**让第一个姿势是一次移动，而不是一跳** |

⛔ **拒绝每道流、每个代码只印一次。** 50 Hz 下每个拒绝都印，会**把最重要的那一行埋掉**——`pose: stream lost after 500 ms — torque released`。

⚠️ **看门狗跑在主循环里，不在控制台任务里**——因为控制台任务会阻塞在 `read()`。**于是两条任务压在一条 UART 上，所以 `servo.cpp` 现在围着总线持一把互斥锁**——⛔ **交错的包不是被拒绝的指令，而是另一条指令，或沉默。**

✅ **同一天测的，±5° 的六个往返:** 678 个姿势，**零拒绝、零 clamp**，看门狗每个往返响一次。**pitch 用 `857` 个十分之一度指令，之前之后都读到 894**——不是印出来的 85.6°（那会回到 893）。⚠️ **每个往返都停在比中心低约六个计数的地方**——与 timed 台架相同的不足。

⛔ **这不意味着: 引擎跑了。** 插值在本仓库之外的主机工具里（`~/stackchan/pose_stream.py`），不在 `engine/trajectory/`。**没有读 `Motion Intent`，传输路径仍然没有选定。** **记录在 `records/2026-10-18-first-arrival.md`。**

⚠️ **流在跑的时候 `bench` 被拒绝**（`bench: refused — a pose stream is running; wait for 500 ms of silence`）——因为 `bench` 会把控制台堵上几秒，**而迟到的姿势，不是姿势**。

### 这块板子上的两次挂起

⛔ **一条写了 `LED_CFG` 第 7 位——厂商的任何驱动都不写的位——的台架命令，停住了控制台、心跳和 USB-Serial-JTAG 的 ROM。USB 设备仍然枚举着。** 恢复的只有拔插；命令被删除，理由留在 `main/leds.cpp` 里: **没有被碰过的寄存器位不是「未使用」，而是「未知」。**

⛔ **第二次挂起来自读取方，不是电线。** `pyserial` 的 open 复位了板子（`rst:0x15 (USB_UART_CHIP_RESET)`），读取方在启动途中失去了流，ROM 不再应答。**守护进程自己的路径——`os.open`、`os.write`、`os.close`，每帧一次——随后单独运行，什么也没有复位。** 控制台是用 `os.open` 和原始 `termios` 读的。⚠️ **一个拉起 DTR 和 RTS 的读取方，正在重启这台机体。**

### 一个行为者，而不是两个

⚠️ **这个个体出厂时在 `ota_0` 里带着一个可以替换 `ota_1` 里应用的厂商应用。** 有一次，擦掉 `otadata` 来启动它，使它连上网络，并向这个仓库的槽开始 OTA。⇒ **先把厂商镜像从板上读出来（5,177,344 字节，SHA-256 `97b176…cf64ab5b`，保存在这个仓库之外的 `~/stackchan/vendor-image/`），然后擦掉了 `ota_0`**（`erase-region 0x20000 0x4f0000`，4.9 秒）。⛔ **那个文件是唯一的副本，没有任何检查覆盖它。**

⚠️ **而控制台的路径不是身份。** 挂起之前是 `/dev/cu.usbmodem1101`，一次拔插之后是 `/dev/cu.usbmodem101`——**相隔十六分钟，同一块板。** 已安装的 plist 指名第二个；下一次拔插可能指名第三个，**而写到不存在的路径的帧被记录为 `sent: false`，不会被抛出。**

## 声音——2026-10-18

✅ **基板播放第四个栏位，而作者四个词都听见了。** 放大器是 I²C `0x36` 上的 **AW88298**，坐在显示器已经拥有的总线上；它的复位是 **AW9523 的 P0.2**，所以 `display::pulse_amplifier_reset()` 持有那次脉冲，`sound` 回调进去——**一条总线，一个所有者。** 音频路径是 `I2S_NUM_0` 作主，**24,000 Hz、16 位立体声**，MCLK 256 × fs。

| 什么 | 厂商的数 | 本仓库改动的 |
|---|---|---|
| 放大器的表 | 按顺序写八个寄存器，`0x00` 的 `0x55AA` 在前，其后 50 ms 的沉默 | ⛔ **没有——没有一个值是在这个个体上测得的** |
| 采样率码 | `0x06` = `0x3CC8`，48,000 Hz 的码 | **`0x3CC5`**——速率码 5，手工写入，使码与 24,000 Hz 的流一致 |
| 音量 | `0x0C` = `0x3064`，厂商的启动 −18 dB | **`0x0C` = `0x1864`，启动 −10 dB**——不是厂商的默认值，而是 2026-10-19 那只耳朵的判定；`bench volume <0..100>` 只改写高字节 |
| 引脚 | MCLK GPIO 0、BCLK 34、WS 33、DOUT 13（DIN 14 未用） | 无 |

⛔ **速率码与采样率不一致，就是一条沉默、音高错误的通道，而板子上没有任何东西报告它**——所以改动的那一个数不留在源码里，而是在这里、在记录里被点名。

⚠️ **四个音是选择，不是测量**——与十二颗 LED 的颜色同一地位。`hello` 上行，`pip` 是一个亮点，`chime` 上行且响得更久，`fall` 下行。**判定它们的只有一对耳朵**，而那个判定只是*被听见了*（`records/2026-10-18-the-voice-zh.md`）。✅ **2026-10-19，同一只耳朵判定了音量**：四个词在厂商的启动音量下是「少し小さい」，而**`fall`——唯一以 440 Hz 收尾的词——比另外三个小**。⇒ **启动音量是 −10 dB，只有 `fall` 以 0.34 写出**（其余为 0.22）；作者再听一次，说了「OK」。⛔ **那是音量的比较，不是音的比较**——形状本身仍然只立在选择上。

## 落地 — 2026-10-19

⛔ **这一节不是记录。** `records/` 里的每一个文件都以人的观察为脊梁；这一节只有板子自己的读回，没有眼睛。**它回答的是头停在了哪里，不是是否有东西在动**——所以它在承载这台机体数字的这份文档里，而不在记录的容器里。

⚠️ **舵机知道自己停得不够。** 读回的位置是舵机自己的当前位置，不是主机的估计——所以停在目标前的是舵机本身，不是传感器看不见的齿轮链。⚠️ **原因没有再往下分开**: 控制不感带和扭矩下的摩擦都符合这些数字；而这个控制台只能读位置，读不到不感带寄存器，这台工作台上也没有量具能把空回与“不驱动最后几个计数的舵机”分开。

⚠️ **速度不是解释。** 流的快速调用（`time=20 speed=0`，四十毫秒间隔的三十个姿势）在目标前七个计数处落地——与慢的台上调用完全相同。

⚠️ **+12 的那一次读数并没有停在 +12。** 在 `bench set 8.0` 之后，头被宣布保持在 497。把同一个目标再写一次，它移到 491，并留在那里。⛔ **那是蠕变，还是重新写入的目标，这里不分**——从另一个进入方向做的重复落在 491，在被看着的五秒里没有移动。

✅ **脖子记录里的那句话，在这台工作台能回答的范围内被回答了**: 落地偏移的大小和符号在两个轴上都被测过，决定符号的是行进方向。⛔ **原因被收窄了，但没有被点名**——不感带与摩擦之间仍然开着，而且是诚实地开着，而不是被指派。

⛔ **什么都没有补偿。** 一个恒定的偏置会在一半的时间里出错——因为符号跟随行进方向；一个带方向的偏置则会成为写进主机或固件的新的机体固有数字。**要不要写、写在哪里，是这里没有作出的决定。**

⚠️ **对接缝意味着什么**: 守护进程把每个身势从它最后写入的姿势开始规划，而头停在那个姿势前六到八个计数处。下一个计划的第一个样本就在同一个地方附近，所以差是有界的、不会跨身势累积——**但两个身势之间的跳变没有被测过**，而且⚠️ **自 0.19.23 起，守护进程在每个身势时向板子询问位置，但在这一台上舵机总线什么也不回答**（`bench scan` → 零台），所以答案不携带姿势。

⚠️ **头留在 yaw 8.0°、pitch 50.0°**——raw yaw 491、pitch 781，扭矩开着。**那就是守护进程相信头所在的那个姿势**，所以下一次流出的身势，会从守护进程以为的起点、在偏移之内开始。

## 电源的开关——2026-10-19

⛔ **直到这一天，`bench power on` 无论扩展器如何对待写入，都会印出 ON。** 命令从未询问写入是否落地——**打印是主张，不是答案。** ⇒ **现在它检查 `leds::servo_power()` 的返回值**，印出 `the expander took the write` 或 `THE EXPANDER DID NOT TAKE THE WRITE`，然后调用 `servo_power_probe()`。

**探针读到的东西**，引脚0，舵机电源轨的使能线:

| 寄存器 | 值 | 含义 |
|---|---|---|
| `M_L` `0x03` | `0x01` | 引脚0是输出 |
| `O_L` `0x05` | `0x01` | 输出为高 |
| `I_L` `0x07` | `0x00` | 输入寄存器把引脚读为低 |
| `PU_L` `0x09` | `0x01` | 上拉开 |
| `PD_L` `0x0B` | `0x00` | 下拉关 |
| `DRV_L` `0x13` | `0xFE` | 推挽 |

⚠️ **写入落地了。本该读出线为高的那一位没有落下。** ⛔ **`I_L = 0x00` 的含义在这里尚未确定**: 扩展器的输入寄存器可能只在引脚为输入时映出焊盘，所以它**与线被拉低**和**寄存器不读输出**两者都相容。⇒ **这个探针合上的是「扩展器收到了写入」。它合不上的是「电源轨有电」。**

⚠️ **推挽试验在同一天写下、又被删掉。** 写 `DRV_L` 使它从 `0xFF` 变成 `0xFE`，输入位仍是 `0x00`，`bench scan` 仍是 **0 id(s)**——**试验改了一个寄存器，总线能听见的东西一个也没改。**

⛔ **扩展器不会被 ESP 的复位带回。** `DRV_L` 跨越一次写入和一次硬复位仍是 `0xFE`: **PY32 的寄存器比 ESP 的一次启动活得更久。** 厂商驱动在启动时写一次，是因为它的启动是板子的第一次启动。⇒ **继承上一次运行寄存器的启动，不是状态已知的启动。** `leds::begin()` 现在在每次启动时写方向、上拉、推挽和水准，然后才接通电源轨。

**而总线比主机更早沉默。** 2026-10-19 第一次捕获的启动日志读出 `servo: ping yaw=0/3 pitch=0/3` 和 `servo: a position did not read — nothing will move`，这一台的 NVS 中心是 **yaw 460、pitch 620**。⇒ **主机写下的任何一行都不是沉默的原因——它从启动时就在。**

⚠️ **同一天又来了两个答案，但都没有合上电源轨。** `bench pmu` 读 AXP2101: `0x00=0x38`、`0x01=0x32`、**`vbat=4624 mV`**、方向 1（充电中）、充电状态 2——**电池在，而且正在充电。** ⛔ **那是 PMIC 的寄存器，不是电源轨的电压。** `bench level` 读两次引脚0的焊盘: **作为带上拉的输入读为 LOW**——外部的某个东西把它拉低，这正是默认为关的使能线通常的样子——而**作为驱动高电平的输出仍然读为 LOW**，⛔ **这要么是寄存器不映出输出，要么是焊盘被重载，这里还分不开。** ⇒ **供电在电池那里；电源开关、VM 的路径和电源轨的实际电压仍未测量**——人下一步能试的是开关，其余由万用表合上。

### 开关，是电源轨自己的电源——2026-10-19

⛔ **剩下的问题是物理的，而其中第一个是被切断电源回答的。** `bench power off`、三秒、`bench power on`，然后 `bench scan`: **2 id(s) 回答了。** ⇒ **电源轨、开关、VM 的路径、扩展器的引脚、配线，从来都不是问题所在。**（关于电源开关的问题，作者已经从外面合上了: 拔掉 USB，屏幕仍然亮着——**机体靠电池运行。**）

⛔ **还没有回答的**: 是什么把舵机放进那个状态。它跟着一次有界的动作出现过一次，而在其他许多分钟里没有出现——**触发条件尚未被名指。而起动时把电源轨转一圈是恢复，不是诊断。**
