✅ **构建了，烧写了，头转过来了——2026-10-18。** 这个目录产出了 `build/stackchan-vessel.bin`，写到 `0x510000`，用哈希核对，然后运行了它: 应用印出 `ready.`，两个舵机都应答了 ping，`bench move 5` 转动了头。✅ **而同一天稍晚，第一次，目标来自主机:** 每 20 ms 一行的 `pose`，共 678 行，零拒绝，看着的作者说「動いた」。✅ **在那之后，十二颗 LED 亮了，并跟着词走**——`warm` 变成橙色，`alert` 变成黄色，`breathe` 变成呼吸——**包括当那个词来自已安装的守护进程、经过传输路、穿过控制台的时候。** ⛔ **下面的拒绝没有改变**——没有任何身势拥有角度，携带身势的帧仍然被拒绝。**记录在 `records/2026-10-18-first-arrival.md` 与 `records/2026-10-18-the-lights.md`，而观察是两者的脊梁。**

**这里有的:** 一个命令帧的解析器，以及一个拒绝所有身势的 `apply_command`。**这里没有的:** 角度。⛔ **把 `perk` 变成舵机位置的数字，不在任何记录里**——厂商源码给出的是度与计数之间的**标度**，那是和**哪个**角度是 `perk` 不同的一个数。

⚠️ **这个拒绝不是某个被忘记写下的行的占位符。** 在手边的个体被测量之前，**它就是那一行**（`docs/first-contact-stackchan.md`）。**猜出来的角度在源码里与测量出来的角度无法区分**——所以一个也不写。

## 帧携带什么

**每条命令一行 JSON**，而命令在机体该显示的东西发生变化时到达——阶段、脸、光或选中的身势；这不是流。⚠️ **脖子只在阶段转换时动**: 身势只在那里被选中。契约是 `schemas/stackchan-command.schema.json`，两端都读它。

| 栏 | 值 | 含义 |
|---|---|---|
| `face` | Pet 的五张脸，或 `null` | 显示这个表情。`null` = 不改变 |
| `light` | `off` / `dim` / `breathe` / `warm` / `alert` / `error` | 始终存在，永不为 `null` |
| `gesture` | `perk` / `nod` / `turn` / `settle` / `flinch`，或 `null` | 动脖子。`null` = 不动 |

⛔ **没有 `sound` 栏。** 扬声器是一个还不存在的通道。

## 厂商源码记录了什么

✅ **自 2026-10-18 起，这些已经在记录里**——`m5stack/StackChan`，分支 `firmware-dev`，MIT：手边个体里装的就是这份固件。⚠️ **这是厂商的数字，从代码里读出，不是在这里测得的。** 本仓库读它，但不拥有它。

| 什么 | 厂商的记录 |
|---|---|
| 舵机总线 | UART1，1,000,000 baud，TX GPIO 6，RX GPIO 7。Feetech SCSCL |
| 标度 | `raw = zero + angle × 16 / 5 / 10`，`angle` 以 0.1° 计 ⇒ **一个计数是 0.3125°**。逆式 `(raw − zero) × 5 × 10 / 16` |
| yaw（ID 1） | 默认零点 460，范围 ±1280（0.1°）= **±128.0°**，raw 0–1000 |
| pitch（ID 2） | 默认零点 620，范围 30–870（0.1°）= **+3.0°〜+87.0°**，raw 0–1000，带堵转保护 |
| 零点 | NVS，命名空间 `servo`，键 `zero_pos_1` / `zero_pos_2`——⚠️ **这台个体的实测零点就在这里** |
| LED | 12 个。在 PY32 IO 扩展器（I²C `0x6F`，SDA GPIO 12，SCL GPIO 11）之后。同一个扩展器在引脚 0 上切 **舵机电源** |

⛔ **至今仍不在任何记录里的，是这个目录拒绝去发明的表：`perk` 是哪个角度。** 标度只教你怎么**发送**一个角度。它不教你**哪个**角度。

## 这份源码故意不决定的事

- **身势表** — `perk` 是哪个角度：没有记录，没有测量，就没有行。✅ **度与计数的标度已经不在这张单子上**——厂商的源码在上面持有它;
- **LED 颜色** — ✅ **顺序是扩展器之后的 RGB565，而自 2026-10-18 起每一种光都有颜色**; ⛔ **每一种都是 `main/leds.cpp` 里的选择，不是关于宠物应该长什么样的测量**;
- **显示渲染器** — 在这里脸是意义，不是像素;
- **传输路径** — ✅ **2026-10-18 决定了，它就是控制台**: 守护进程打开 USB 串口路径，每帧写一行，然后关闭。⛔ **不保持打开，所以帧与帧之间 `bench` 和 `idf.py` 仍然拥有端口。** ⚠️ **这个路径不是跨拔插稳定的名字**——见[光](#光--2026-10-18)。

## 舵机的 time 字段回答了什么 — 2026-10-18

✅ **`bench timed <yaw_deg> <time> [speed]` 被加进台架，并在同一天烧入。** 它**只写一次**目标——带着 time 字段和 speed 字段——与每秒重写目标的 `bench move` 不同——**然后每 200 ms 读一次 yaw 轴，最多 70 秒。**

⛔ **在这台机器上，time 字段没有决定移动时间；决定它的是 speed 字段。** 两次试次：`time=5000, speed=0` 走了 5 个计数就停住；`time=500, speed=100` 以约 127 计数/秒，在约 0.3–0.4 秒内走了 32 个计数（10°）。**两次都恰好停在距目标 6 个计数处**——看上去是固定的偏移，与间隙、与回读本身都还没有分开。

⇒ **对引擎的意义，一行：在这台机器上，柔和不能委托给舵机。** 没有台阶的脖子，**需要主机持续写插值后的目标**——`engine/trajectory/` 正是为此而在，**而它在这台机器上从未跑过。** ⚠️ **数字在 `records/2026-10-18-first-arrival.md` 里，那里作为背骨的是伴随数字的观察。**

## 姿势那一行，而基板读它——2026-10-18

✅ **`pose <yaw_tenths> <pitch_tenths>*<CC>` 的基板端在 `main/main.cpp` 里。** 靠第一个词分发，**正是主机编码器所假设的那样**，它做五件事:

| 什么 | 怎么做 |
|---|---|
| 长度 | 超过 **64** 字节 → `pose: refused (too-long)` |
| 校验和 | 最后一个 `*` 之后两位十六进制，必须等于它之前全部字节的和 `& 0xFF` |
| 字段 | 恰好一个空格，**两栏都按与 Python 解码器相同的拼写规则解析**——`05`、`-0`、`+5` 全部拒绝 |
| clamp | 对着**这台机器**的界限（`board::kYawAngleLimitTenths`、`kPitchAngleMin/MaxTenths`），而不是协议的界限 |
| 第一行 | 把两个目标都设成当前位置、开扭矩、等 200 ms——**让第一个姿势是一次移动，而不是一跳** |

⛔ **拒绝每道流、每个代码只印一次。** 50 Hz 下每个拒绝都印，会**把最重要的那一行埋掉**——`pose: stream lost after 500 ms — torque released`。

⚠️ **看门狗跑在主循环里，不在控制台任务里**——因为控制台任务会阻塞在 `read()`。**于是两条任务压在一条 UART 上，所以 `servo.cpp` 现在围着总线持一把互斥锁**——⛔ **交错的包不是被拒绝的指令，而是另一条指令，或沉默。**

✅ **同一天测的，±5° 的六个往返:** 678 个姿势，**零拒绝、零 clamp**，看门狗每个往返响一次。**pitch 用 `857` 个十分之一度指令，之前之后都读到 894**——不是印出来的 85.6°（那会回到 893）。⚠️ **每个往返都停在比中心低约六个计数的地方**——与 timed 台架相同的不足。

⛔ **这不意味着: 引擎跑了。** 插值在本仓库之外的主机工具里（`~/stackchan/pose_stream.py`），不在 `engine/trajectory/`。**没有读 `Motion Intent`，传输路径仍然没有选定。** **记录在 `records/2026-10-18-first-arrival.md`。**

⚠️ **流在跑的时候 `bench` 被拒绝**（`bench: refused — a pose stream is running; wait for 500 ms of silence`）——因为 `bench` 会把控制台堵上几秒，**而迟到的姿势，不是姿势**。

## 光 — 2026-10-18

✅ **十二颗 LED 工作了，来自守护进程的帧能到达它们。** ⛔ **同一天早些时候它们没有工作**——一个板子接受了的帧产生了「光っていない」，而扩展器的寄存器保持着完全正确的颜色。**记录在 `records/2026-10-18-the-lights.md`，而观察是它的脊梁。**

| light | 颜色（RGB565 源） | 在哪里选的 |
|---|---|---|
| `off` | `{0, 0, 0}` | `main/leds.cpp` |
| `dim` | `{24, 24, 40}` | `main/leds.cpp` |
| `breathe` | `{40, 48, 72}`，3 秒内 20%〜100% 的三角波 | `main/leds.cpp` |
| `warm` | `{112, 64, 24}` | `main/leds.cpp` |
| `alert` | `{160, 104, 0}` | `main/leds.cpp` |
| `error` | `{144, 0, 0}` | `main/leds.cpp` |

⛔ **其中没有一个测量。** 十二颗被写到 I²C `0x6F` 的 PY32 IO 扩展器之后: `0x24` 的 `LED_CFG` 在位 0〜5 持有数量、位 6 持有 refresh，像素从 `0x30` 起是 RGB565 小端。

✅ **`bench leds` 是为了把一个疑问变成两个而加的。** 它读回扩展器——版本、`LED_CFG`、数据脚之后的六个寄存器、前四个像素——然后把十二颗全部写成全红，再读一次像素 0。**「寄存器接受了值」和「像素亮着」被分开来问，两种答案都会被印出来。**

⚠️ **改变了结果的只有一件事，而它是假设:** 扩展器被断电重新初始化了。板子为了从挂起中恢复被拔下，插回之后，**在没有新代码的情况下**十二颗亮了。⛔ **这里没有把断电与插上、重新枚举、以及之前刚发生的重烧区分开来。**

### 这块板子上的两次挂起

⛔ **一条写了 `LED_CFG` 第 7 位——厂商的任何驱动都不写的位——的台架命令，停住了控制台、心跳和 USB-Serial-JTAG 的 ROM。USB 设备仍然枚举着。** 恢复的只有拔插；命令被删除，理由留在 `main/leds.cpp` 里: **没有被碰过的寄存器位不是「未使用」，而是「未知」。**

⛔ **第二次挂起来自读取方，不是电线。** `pyserial` 的 open 复位了板子（`rst:0x15 (USB_UART_CHIP_RESET)`），读取方在启动途中失去了流，ROM 不再应答。**守护进程自己的路径——`os.open`、`os.write`、`os.close`，每帧一次——随后单独运行，什么也没有复位。** 控制台是用 `os.open` 和原始 `termios` 读的。⚠️ **一个拉起 DTR 和 RTS 的读取方，正在重启这台机体。**

### 一个行为者，而不是两个

⚠️ **这个个体出厂时在 `ota_0` 里带着一个可以替换 `ota_1` 里应用的厂商应用。** 有一次，擦掉 `otadata` 来启动它，使它连上网络，并向这个仓库的槽开始 OTA。⇒ **先把厂商镜像从板上读出来（5,177,344 字节，SHA-256 `97b176…cf64ab5b`，保存在这个仓库之外的 `~/stackchan/vendor-image/`），然后擦掉了 `ota_0`**（`erase-region 0x20000 0x4f0000`，4.9 秒）。⛔ **那个文件是唯一的副本，没有任何检查覆盖它。**

⚠️ **而控制台的路径不是身份。** 挂起之前是 `/dev/cu.usbmodem1101`，一次拔插之后是 `/dev/cu.usbmodem101`——**相隔十六分钟，同一块板。** 已安装的 plist 指名第二个；下一次拔插可能指名第三个，**而写到不存在的路径的帧被记录为 `sent: false`，不会被抛出。**
