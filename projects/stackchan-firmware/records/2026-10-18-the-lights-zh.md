# 光 — 2026-10-18

⛔ **观察是这份文件的脊梁。程序的数字被引用在它的内部作为证据，而不是在它的周围。** 一个只保存程序输出了什么的日志，无法回答这份记录存在的理由——**灯是否亮了**——**而且它读起来像证据。**

**数了什么。** 一块板子、一天、一双眼睛。**没数什么：** 亮度、色温、另一个观察者会把每种颜色叫什么，以及这十二颗之外有没有别的光在亮。

## 最初的帧，和没有亮的光

同一天早些时候，主机第一次发到这个个体的帧载着 `light=dim`，板子接受了它，**却什么也没有亮。** 同样的写入随后由台架命令 `bench leds` 执行，并读了回来：

```
leds: ready=1 version=0x41 cfg=0x0C
leds: M_H=0x20 (pin 13 set)
leds: PU_H=0x20 (pin 13 set)
leds: DRV_H=0x1F (pin 13 clear)
leds: pixel 0 = 0x18C5 (r=3 g=6 b=5)
leds: wrote full red to 12, refresh ok; pixel 0 now 0xF800
```

**数字说的话：** 扩展器保持着正确的数量（`cfg=0x0C`，十二颗），数据脚是输出，带上了上拉和推挽，前四个像素保持的颜色是 `0x18C5`——**`{24, 24, 40}` 的 RGB565，正是这个仓库选择的 `dim` 颜色**。全红写入读回来是 `0xF800`，没有错误。

⛔ **而看着这十二颗的作者说，「光っていない」。** 寄存器保持着颜色，像素却没有显示它。**在那之前，这两件事是同一个词。分开的，就是这一天。**

## 改变了结果的是什么——而没有改变的是什么

光开始生效之后只有**一件事**，那一天余下的部分与它不矛盾：**扩展器被断电重新初始化了。** 板子为了从一次挂起中恢复（见下）被拔下，再插上时，**没有新的代码、没有新的构建、没有新的写入，十二颗亮了。**

⛔ **那是假设，不是发现。** 这里没有把断电与插入的那一刻、重新枚举、以及之前刚烧过固件区分开来。**能作为发现、狭窄地说出来的只有这一点：** 在那个周期之前，无论寄存器内容多么正确都不成光；那个周期之后，每一次写入都成了光。

⚠️ **同一天，在那之前调色板被乘以四。** 最初的值写于这台个体的 LED 还没有被任何人看过的时候，`r=28/255` 的暖色在日光下是看不见的。**词与词之间的比例没有改变，动的只是尺度。** ⛔ **这些颜色没有一个测量。**

## 两次让机体停下的挂起

**第一次，来自一个未知的寄存器位。** 台架命令写了 `LED_CFG` 的第 7 位——厂商的任何驱动都不写的位——并保持了三秒。控制台停了，心跳停了，USB-Serial-JTAG 的 ROM 不再回应 esptool，而 USB 设备仍然枚举着。**恢复的只有拔插。** 命令被删除，理由留在 `main/leds.cpp` 里：**没有被碰过的寄存器位不是「未使用」，而是「未知」。**

**第二次，来自一次不是读取的读取。** 同一天，主机用 `pyserial` 打开控制台，想看守护进程写出的帧是否会到达。打开的一瞬间板子复位了（捕捉里有 `rst:0x15 (USB_UART_CHIP_RESET)`），读取方在启动途中失去了流，之后控制台什么也不送出，esptool 返回 `No serial data received`，而 USB 设备仍然枚举着。**征兆与第一次挂起相同，拔插又一次恢复了它。**

⛔ **第二次看起来像是新传输路的错。而它不是。** 守护进程的写入路径——`os.open`、`os.write`、`os.close`，每帧一次——随后**单独**运行。控制台不用 `pyserial`，而用 `os.open` 和原始 `termios` 来读：

```
10.05 frame: light=dim face=none
```

`alive` 在整个窗口里每三秒继续一次，没有启动横幅，也没有中断。⇒ **守护进程自己的 open、write、close 送出了那一行，没有复位板子。复位它的是 `pyserial` 的 open，而之后是什么让它停下，没有被确定。**

⚠️ **代价要指名：** 一个拉起 DTR 和 RTS 的工具打开的端口，就是一次复位。而启动途中的复位，在这块板子上不是免费的。**下一个想看控制台的读取方，应该用 `os.open` 和 `termios`，或者承认自己在重启机体。**

## 守护进程写，板子回答

✅ **随后守护进程被给了端口，并按安装好的样子运行**——launchd 的任务、已安装的 plist、一条路径。向它的套接字发送一个事件，捕捉显示了两端：

```
frame: light=warm face=greeting (no renderer yet)
frame: gesture perk refused — no gesture -> angle table exists
```

- **守护进程的日志保持着同一个帧**——`{"frame": "{\"face\":\"greeting\",\"gesture\":\"perk\",\"light\":\"warm\"}", "sent": true, …}`；
- **板子收到了它**——因为板子自己的控制台把它印了出来；
- **手势被板子拒绝了**——正如 `command_frame.cpp` 所写的那样。而拒绝没有让光停下；
- **什么也没有复位，什么也没有挂起。**

⇒ **这是这个仓库的帧，第一次经过传输路到达机体，而且两端都被观察到了。** ⛔ **只有 `sent: true` 说不出这一点**——它说的是主机的 tty 接受了字节，而今天这两个主张分开了一个小时。

⚠️ **而词就是帧的全部。** 这一行载着 `face`、`light`、`gesture`，别的什么也没有。⛔ **这个进程不送出任何数字：姿态行有它自己的编码器，守护进程不写它。**

⚠️ **作者的「黄色のled」是一个帧，不是故障。** 守护进程的日志显示那一刻是 `light=alert`——调色板里的 `{160, 104, 0}`。而下一帧 `light=breathe`，作者称它为「その後呼吸」。**为一个词选的颜色，就以那个颜色到达了，而眼睛给它命了名。**

## 端口的名移动了

⚠️ **plist 里的路径不是身份。** 挂起之前它指向 `/dev/cu.usbmodem1101`，线缆回来之后指向 `/dev/cu.usbmodem101`——**在同一块板子上，相隔十六分钟测得的。** 已安装的 plist 指名的是第二个；**下一次拔插可能指名第三个。** ⛔ **写到已不存在的路径的帧被记录为 `sent: false`，不是错误**——这是安全的，同时也是沉默的。**备忘里的陷阱，现在是被测量的，而不是被引用的。**

## 机体的另一个行为者发生了什么

⚠️ **这个个体装着两个应用，而 `ota_0` 里的那个可以替换另一个。** 有一次，擦掉 `otadata` 来启动它，使它连上网络，并开始向 `ota_1`——这个仓库自己的槽——做 OTA。拔线是在那途中做的。

⇒ **先把厂商镜像从板上读出来，然后擦掉了 `ota_0`。**

| 什么 | 值 |
|---|---|
| 文件 | `~/stackchan/vendor-image/stack-chan-1.4.4-ota0.bin`，**在这个仓库之外** |
| 大小 | **5,177,344 字节**（0x4f0000） |
| SHA-256 | `97b176049d75a3e1851ccc738003b62b3b3938c636f7edb2ba287296cf64ab5b` |
| 开头的字节 | `e9 06 02 4f`——ESP 镜像的魔数 |
| 擦除 | `erase-region 0x20000 0x4f0000`，**4.9 秒** |

⚠️ **分区表仍然列着 `ota_0`。区域是空的。** ⛔ **擦掉它没有让板子更安全或更危险——它只是让机体从一个行为者变成两个。** ⚠️ **而那个文件是这个工房持有的唯一副本：不在仓库里，也没有任何检查覆盖它。**

## 这份记录不确定的事

- **不确定引擎跑过。** 没有读 `Motion Intent`，没有计算轨道，没有通过门。**光回答的是词；它不计算运动。**
- **不确定 `alert` 是好颜色，也不确定 `breathe` 是好呼吸。** 每一种颜色都是 `main/leds.cpp` 里的选择，没有一个是测量。
- **不确定最初的写入为什么没有成为光。** 能指名的差别只有断电，而那是假设。
- **不确定 `pyserial` 会让这块板停下。** 只观察到它让板子复位了一次。复位之后发生了什么，没有被确定。
- **不确定宠物在那里。** ⛔ **那是目标，在这个工房里无法验证。** 跟随词的光是机构，不是存在。
