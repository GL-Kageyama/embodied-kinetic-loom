# 没有线缆的机体 — 2026-10-21

⛔ **观察是这一页的脊梁。程序的数字不是围绕它写，而是作为证据引用在其中。** 守护进程写下的一行，不是动过的头。

**数了什么。** 机体一台、Mac 一台、接入点一个、套接字一条，并且**任何时刻都没有 USB 线缆**: 下面全部的测量期间 `/dev/cu.usb*` 都不存在，`system_profiler SPUSBDataType` 里也没有列出 JTAG 设备。**没数什么:** 屏幕——⛔ **这期间房间里没有眼睛**——Wi-Fi 断开、接入点重启、Mac 地址的变化、抓包。下面的每个数字都读自日志，或读自基板自己印出的行。

## 被问的是什么

「線を抜くよ？」——然后「抜いた」——然后「今後は、給電だけ用にどこかのコンセントに繋いでおくね」。

⚠️ **最后那一句不是测试，是这台机体将要生活的配置。** ⇒ **一个打开 `/dev/cu.usbmodem101` 的守护进程，一条路都没有。** 在这里链路不是改进，**而是机体剩下的唯一通路。**

## 看见了什么

**Mac 分不清「控制台没了」和「基板没了」。** 旧的作业继续运行，继续写行:

```
{"frame": "{...}", "sent": false, "accepted": null, "err": "ENOENT", ...}
```

⛔ **`ENOENT` 是主机自己缺失的文件，不是基板的沉默**——而到这一页为止，日志里没有任何东西区分这两者。

**每当监听消失，基板就自己重新拨号。** 换手四次，拨号四次——端口回来之后 **0.3 秒到 4 秒**:

```
1792527289.638 accepted 192.168.0.19:50836
1792527566.570 accepted 192.168.0.19:50840
```

**守护进程现在等它，而机体的全部对话都走过这一条套接字。** `bench pos` 在链路上被回答，帧的受理行回来了，动作流了出去——**线缆不在的状态下，全部发生在同一个事件里**:

```
{"link": "the board dialled in", "peer": "192.168.0.19:50841"}
{"position": [331, 500], "heard": true, "read": "bench: yaw=ok pitch=ok ...", "at": 9971.837653958}
{"neck": "look_up", "from": [331, 500], "to": [80, 500], "poses": 22, "at": 9971.837653958}
{"neck": "look_up", "applied": 22, "late": 21, "held": 27, "at": 9972.958619791}
{"neck": "look_up", "verdict": {"applied": 49, "refused": 0, "clamped": 0}, "at": 9974.254092916}
{"position": [96, 500], "heard": true, "read": "bench: yaw raw 491, angle 9.6 deg (zero 460) ..."}
```

✅ **头动了。** yaw 在动作前读到 **33.1°**、动作后读到 **9.6°**，而基板自己的汇总——**49 applied**——与主机的 **22 applied + 27 held** 恰好相等。⚠️ **那个一致，就是 0.19.38 的规则在线缆上成立的那样、在套接字上也成立**，而且这是第一次在无线缆的状态下被检查。

**而在线缆上测得的等待，没有挺过这段旅程。** 最初两次什么也没听到:

```
{"position": null, "heard": false, "read": "", "at": ...}
```

越过链路的 10 次 `bench pos`，在监听一侧计时:

| 询问 | `bench: yaw=ok` 到达 | 位置行到达 |
|---|---|---|
| 1 | +0.441 秒 | +0.471 秒 |
| 2 | +0.640 秒 | +0.803 秒 |
| 3 | +0.331 秒 | +0.345 秒 |
| 4 | +0.461 秒 | +0.474 秒 |
| 5 | +0.479 秒 | **+1.045 秒** |
| 6 | +0.723 秒 | +0.861 秒 |
| 7 | +0.299 秒 | +0.418 秒 |

⚠️ **发送了十次，表里有七次**——最后三次是在记录关闭的过程中写出的，答案没有留下。⛔ **这是这一页的限度，不是沉默询问的计数。**

⛔ **`PORT_WAIT = 0.5` 是针对线缆测得的数字，它不会跟着询问一起走。** ⇒ **`LINK_WAIT = 1.5`** 成了链路上探针的上限。而慢的基板成了一个测试: `SlowBoard` 在 0.7 秒后回答，位置被读到。

**判定窗口以同样的方式落到外面去了。** 22 个姿势用 **0.526 秒**写完:

```
1792527570.448  sent b'pose 96 500*FB\n'
1792527570.860  recv pose: stream started — goals on the present positions (yaw 565, pitch 780), torque on
1792527570.950  sent b'pose 350 500*24\n'
1792527571.938  recv pose: stream lost after 500 ms — torque released
1792527572.097  recv pose: 22 applied, 0 refused, 0 clamped
```

⛔ **基板自己的汇总，在写完最后一个姿势之后 1.647 秒才到达**——落在 `VERDICT_WAIT = 1.5` 之外，第一次实机运行因此留下了 `verdict: null`。⇒ **`LINK_VERDICT_WAIT = 3.0`**，而⚠️ **这是放在测量之上的余量，不是测量值。**

**22 个姿势里有 21 个是延迟应用的。** ⛔ **位置到达了，日程表没有到达。** 20 ms 间隔的流，不是这条链路能承载的东西——而主机和基板都没有掩盖它。

## 没有说什么

- ⛔ **链路没有被认证。** 任何能到达 Mac 3333 端口的东西，都能动头、点灯、让扬声器响。**当机体的唯一线缆是 USB 线时，这种暴露并不存在。** ⚠️ **基板在链路上拒绝的只有 `bench wifi` 和 `bench dial`，帧和姿势直接通过。**
- ⛔ **基板的自语不过链路。** 通过的只有走 `Say()` 的行——`bench:`、`pose:`、`frame:`。`servo: silent for 3 checks…`、`servo: present …` 和启动横幅都是 `printf`，**在线缆之外，已经没有人读它们了。** ⇒ **这台主机再也无法知道伺服总线沉默了**——而那正是 0.19.34 被建成答案的那个故障。
- ⛔ **`let go` 一次也没有被记录。** 今天观察到的断开全是守护进程的替换，**切开链路的那一侧先死了。** 基板自己挂断时的那一行，还不存在。
- ⛔ **位置到达，不等于日程到达。** 22 个里 21 个迟了。**头在计划结束的位置上，而不在计划说的时间上。**
- ⛔ **「没有线缆也能活下来」不是这里测的东西。** 测的是**只靠供电的机体，被守护进程越过链路驱动，并用基板自己的数字作答**。⚠️ **Wi-Fi 断开、接入点重启、Mac 地址变化都未测量**，而基板拨号的地址，是一条没有控制台就说不出口的 DHCP 租约。
- ⚠️ **拔掉线缆之后，没有人再看过那块屏。** 脸、光、声音，在这里只作为**基板受理了的帧**被主张，没有被主张成一个人看见的东西。
