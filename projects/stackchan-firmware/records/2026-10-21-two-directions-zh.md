# 两个方向 — 2026-10-21

⛔ **这份文件的脊梁是观察。程序的数字被引用在它内部作为证据，而不是围着它。** 主机的 `sendto` 接受了的数据包，不是到达基板的数据包。

**数了什么。** 一台机体、一台 Mac、一个接入点、一个有線端口，以及一整晚两个方向上的尝试。**没有数什么:** 第二台无线客户端、第二个接入点、抓包——**没有 root 这些都拿不到，所以线上的帧一帧也没看见。** 下面每一句，都是从两端各自的报告推出来的。

## 被问的是什么

这一回作者的交待只有一行——**「そもそもwifi接続できているか？の確認あたりから始めて」**。

## 看到的

**电台是连上的。** 基板用自己的话说出来:

```
wifi: nvs holds "BFW6K-G-48420" — connecting
wifi: associated — waiting for an address
wifi: connected ip=192.168.0.19
wifi: credentials "BFW6K-G-48420", associated, 192.168.0.19
wifi:   ch 1 rssi -60
```

**这一行之前先付出了一个启动循环。** 每一次启动都在地址到达大约一秒后死掉——`LoadProhibited`，一条从队列指针出发的 `l32i`，而那个指针的字段里装着 PS 寄存器的值。**core dump 点出了那次死亡**: 任务是 `sys_evt`，被打断在 `esp_netif_lwip_ipc_call_get_netif` 里——那正是 `IP_EVENT_STA_GOT_IP` 处理函数所调用的 `esp_netif_get_ip_info` 背后的 IPC 往返——而它的栈已经越过自己的末端跑进了堆。这个任务的栈是 `CONFIG_ESP_SYSTEM_EVENT_TASK_STACK_SIZE`，**默认 2304**。抬到 4096 之后，同一个处理函数报告 **`sys_evt stack, 1600 bytes never used`**，所以需要的量约 2496，比默认多了大约 200。

## 一次也没有走通的方向

**从 Mac 到基板，什么都没有送到。** 下面这些没有一样到达:

| 试了什么 | 结果 |
|---|---|
| 对 `192.168.0.19:3333` 的 `connect()`，33 次 | `EHOSTUNREACH`，**每次 0.0001–0.0002 秒** |
| 同样的事，从绑定到 `en0` 的套接字 | 一样；基板数到 `0 datagram(s)` |
| UDP 的 `sendto()`，**无论哪个端口**——3333、9999、40000、1 | 一样，而且是瞬间 |
| 不绑定、绑到 `0.0.0.0`、绑到 Mac 自己的地址 | 一样 |
| 对 `192.168.0.255:3333` 的子网广播 | **发出去了，而基板什么也没听见** |
| 9 秒内 87 次 `connect()`，中途还有一帧从基板到达 | **开了 0 次** |

⚠️ **那个拒绝是主机的，不是网络的，所以这里要这样写。** 它在 **0.1 毫秒**内返回——太快了，帧还来不及出去、答案还来不及回来。路由存在而且是新的（`route get` 返回 `UP,HOST,DONE,LLINFO,WASCLONED,IFSCOPE,IFREF`、`expire 1182`），而且**`arp -an` 全程握着这台基板自己的 MAC `80:45:6b:54:6d:b0`**——而一个真的不在的机器显示的是 `(incomplete)`。⇒ **Mac 拿着正确机器的正确地址，仍然拒绝先开口。**

**在同一分钟里、用同一批绑定套接字跑的对造:**

- 网关 `192.168.0.254`——到 80 端口的 `connect()` **0.005 秒就开了**，到 53 端口的 UDP 查询**答了，17 字节**;
- 给基板换的第二个新地址（`192.168.0.77`，只限那次启动）——**也被拒绝**。⇒ 这不是一条过期的缓存项。

⛔ **基板发出的无偿 ARP 什么也没改变。** 它把自己的地址广播给了整个网段（`net: announced this address to the whole segment`），接下来的 33 次和之前分毫不差地失败。

## 每次都走通的方向

**基板先送出去的东西都到了，回音也回来了。**

- 一个 UDP 出去——Mac 从 `192.168.0.77:61530` 读到 `b'still-there'` 并回应，基板印出 **`net: reply "pong"`**;
- **一条由基板向外打开的 TCP 连接**——Mac 接受了它，读到 `b'can-you-hear-me\n'`，回应，基板印出 **`net: the host said "yes-loud-and-clear"`**。

⇒ **一条连接，由基板打开，载住了两个方向。** ⚠️ 这一回所有的成功，都是基板打开的水流里的回应；所有的失败，都是 Mac 想要先开口。

## 没有声称的事

- ⛔ **Mac 为什么拒绝，还没弄清楚。** 0.1 毫秒只说明判断下在主机这边，并不说明是谁下的。没有抓包，也没有第二台客户端来把「这台基板」和「任何无线客户端」区分开。
- ⛔ **这不是对接入点的诊断。** 从来没有直接问过 AP。它只是被当作**可能性**点了一下，仅此而已。
- ⛔ **稳定性没有测。** 上面所有结果都来自一晚、一台、一个 AP、一个有線端口。**这里一个字也没说向外那个方向能维持一小时。**
- ⛔ **这里也没有运输方式的决定。** 被证明的只是方向。在这个方向上建什么、当两条路径都能抵达身体时由谁持有身体，这一页决定不了。
- ⚠️ **用来测它的那个探针不是功能。** `main/net.cpp` 接受连接并回答长度，它从不分发行——因为控制台已经持有身体，而在一条总线上放第二个写手，正是 0.19.27 量到的失败。
