# 二つの向き — 2026-10-21

⛔ **このファイルの背骨は観察である。プログラムの数は、その内側に証拠として引用される。** ホストの `sendto` が受け付けたパケットは、基板に届いたパケットではない。

**数えたもの。** 1台、1つの Mac、1つのアクセスポイント、1つの有線ポート、そして両方向への一晩の試行。**数えていないもの:** 2台目の無線クライアント、2台目のアクセスポイント、パケットキャプチャ——**root 無しではどれも手に入らないので、線の上の枠は一度も見ていない。** 以下の文はすべて、両端が報告したことからの推論である。

## 何を問われたか

この回の著者の指示は一行だった——**「そもそもwifi接続できているか？の確認あたりから始めて」**。

## 見えたもの

**ラジオは繋がっている。** 基板が自分の言葉でそう言う:

```
wifi: nvs holds "BFW6K-G-48420" — connecting
wifi: associated — waiting for an address
wifi: connected ip=192.168.0.19
wifi: credentials "BFW6K-G-48420", associated, 192.168.0.19
wifi:   ch 1 rssi -60
```

**その一行の前に、起動ループを1つ払っている。** どの起動もアドレスが来ておよそ1秒後に死んでいた——`LoadProhibited`、キューへのポインタからの `l32i` で、そのフィールドには PS レジスタの値が入っていた。**コアダンプがその死を名指しした**: タスクは `sys_evt`、割り込まれた先は `esp_netif_lwip_ipc_call_get_netif`——`IP_EVENT_STA_GOT_IP` のハンドラが呼んでいた `esp_netif_get_ip_info` の裏の IPC 往復である——そしてスタックは自分の終端を越えてヒープへ走っていた。このタスクのスタックは `CONFIG_ESP_SYSTEM_EVENT_TASK_STACK_SIZE`、**既定は 2304**。4096 に上げると、同じハンドラが **`sys_evt stack, 1600 bytes never used`** と報告する。つまり必要量は約 2496 で、既定をおよそ 200 超えていた。

## 決して通らなかった向き

**Mac から基板へは、何ひとつ届かなかった。** 以下はどれも届いていない:

| 試したこと | 結果 |
|---|---|
| `192.168.0.19:3333` への `connect()`、33回 | `EHOSTUNREACH`、**1回あたり 0.0001–0.0002 秒** |
| 同じことを `en0` に束縛したソケットから | 同じ。基板は `0 datagram(s)` と数えた |
| UDP の `sendto()`、**どのポートでも**——3333、9999、40000、1 | 同じ。即座に |
| 束縛無し、`0.0.0.0` への束縛、Mac 自身のアドレスへの束縛 | 同じ |
| `192.168.0.255:3333` へのサブネットブロードキャスト | **送信された。そして基板は何も聞いていない** |
| 9秒間に 87回の `connect()`、その途中で基板からの枠が1つ到着した | **開いたのは 0回** |

⚠️ **その拒否はネットワークのものではなくホストのものであり、だからこう書く。** 戻ってくるまでが **0.1 ミリ秒**である——枠が出て答えが返るには速すぎる。経路は存在し、新しかった（`route get` は `UP,HOST,DONE,LLINFO,WASCLONED,IFSCOPE,IFREF`、`expire 1182` を返した）、そして**`arp -an` はその間ずっとこの基板自身の MAC、`80:45:6b:54:6d:b0` を持っていた**——本当に居ないホストは `(incomplete)` と表示されたのに。⇒ **Mac は正しい機械の正しいアドレスを持ったまま、それでも先に喋ることを拒んだ。**

**同じ分に、同じ束縛ソケットで走らせた対照:**

- ゲートウェイ `192.168.0.254`——ポート80への `connect()` は **0.005 秒で開き**、ポート53への UDP 問い合わせは **17 バイトで答えた**;
- 基板に与えた2つ目の新しいアドレス（`192.168.0.77`、その起動限り）——**これも拒否された**。⇒ 1つの古いキャッシュ項目の問題ではない。

⛔ **基板からの無償 ARP は何も変えなかった。** 基板は自分のアドレスをセグメントへブロードキャストし（`net: announced this address to the whole segment`）、その後の33回は以前と寸分違わず失敗した。

## 毎回通った向き

**基板が先に送ったものは届き、答えは戻ってくる。**

- UDP を1つ外へ——Mac は `192.168.0.77:61530` から `b'still-there'` を読み、答え、基板は **`net: reply "pong"`** と印字した;
- **基板が外へ開いた TCP 接続**——Mac は受け入れ、`b'can-you-hear-me\n'` を読み、答え、基板は **`net: the host said "yes-loud-and-clear"`** と印字した。

⇒ **1本の接続が、基板から開かれたものとして、両方向を運んだ。** ⚠️ この回の成功はすべて、基板が開いた流れの中の返信であり、失敗はすべて、Mac が先に喋ろうとしたものだった。

## 言っていないこと

- ⛔ **Mac がなぜ拒むのかは分かっていない。** 0.1 ミリ秒は、判断がホスト側で下されていることしか言わない。何が下しているかは言わない。パケットキャプチャは取っておらず、「この基板」と「どの無線クライアントでも」を分ける2台目も無かった。
- ⛔ **これはアクセスポイントの診断ではない。** AP に直接問い合わせたことは一度も無い。**可能性**として名指ししてあるだけで、それ以上ではない。
- ⛔ **安定性は測っていない。** 上の結果はすべて、一晩、1台、1つの AP、1つの有線ポートのものである。**外へ向かう向きが1時間保つとは、ここでは何も言っていない。**
- ⛔ **ここには輸送の決定も無い。** 証明されたのは向きだけである。その上に何を建てるか、二つの経路が同時に体に届きうるときに誰が体を持つかは、この頁では決まらない。
- ⚠️ **これを測った探針は機能ではない。** `main/net.cpp` は接続を受け、その長さを答えるだけで、行を決してディスパッチしない——コンソールが既に体を持っており、1本のバスに2人目の書き手を置くことが 0.19.27 の測った失敗だからである。
