# projects/stackchan/ —— 电线之上的层

**它决定机器人正在做什么、戴着哪张脸、发什么颜色的光、意味着哪个身势。它不决定任何东西移动多远。**

⛔ **它没有机器 2 的任何数字，也不借用机器 2 的数字。** 手边这一台的零点、符号与框架，都不在这个包里。⇒ **它选择的每一个身势都是一个词，而词变成数字发生在机体那一侧**——`projects/stackchan-firmware/main/main.cpp`，2026-10-18 在手边这一台上测得的（`projects/stackchan-firmware/records/2026-10-18-the-gestures.md`）。`Decision.sent` 为 `True`，只在点了端口、并且主机的 tty 收下了整行的时候。

⚠️ **Stack-chan 的路线中，一行固件都不用烧就能检查的部分，就在这里。** 从事件到阶段的对应不需要机体测量；运动需要。**这一层建在检查能响的那一侧。**

✅ **2026-10-18 的四项裁定就是这一页的形状：** 机器人是**伙伴**，不是镜子；**只有转换时身体才动**；电线运送的是**身势命令**，不是 20 ms 的流；并且**十二个 RGB LED 是一等通道，始终亮着**。

## 连着什么，没连着什麼

✅ **它 import Pet 的 `State`，不是复制。** 五张表情只画过一次（决定 A，`projects/pet/expressions.py`）。第二套就是对同一个问题的第二个答案。

✅ **自 2026-10-18 起，它连到了机体**——守护进程每帧把一行写进板子的控制台——**而在此之前没有连上。** ⛔ **这条连接是单向的，每帧只运一行**：这一层自己不打开任何东西，⚠️ **自 0.19.23 起只读回一样东西——身势瞬间所问的 `bench pos` 的答案**——除此之外只能说主机的 tty 收下了整行。检查之外的消费者是它自己的 CLI、守护进程的日志，以及守护进程点名的端口。⚠️ **它在 2026-10-18 之前也没有连到 Claude Code。** ✅ **自那以后就连上了**——`~/.claude/settings.json` 的全部三十三个事件都运行 `projects/stackchan/hook/`，而 launchd 用户代理在登录时启动守护进程。⛔ **这个目录是层，不是安装**：这里的 plist 是副本，记录在 `docs/stackchan-daemon.md`。

## 六个阶段

**五张脸是 Pet 的，六个阶段是这一层的。** 阶段是机器人正在做的事，脸是它显示出来的东西。

| 阶段 | 进入的事件 | 脸 | 光 | 身体 |
|---|---|---|---|---|
| `present` | 表情到期，或醒来 | `curious` | `breathe` | 不动 |
| `greeting` | `SessionStart` | `greeting` | `warm` | `look_up` |
| `working` | `UserPromptSubmit` | `curious` | `dim` | **不动** |
| `blocked` | `PermissionRequest` | `curious` | `alert` | `look_side` |
| `closing` | `Stop` / `StopFailure` | `happy` / `angry` | `warm` / `error` | `nod` / `recoil` |
| `resting` | 90 秒没有事件，或 `SessionEnd` | `sleepy` | `off` | `rest`（只在离开时） |

⚠️ **支撑 `working` 的，是它不用身体表达的二十五个事件。** `PreToolUse` 和 `PostToolUse` **不用身体表达，但确实被接收了**——**每一次都会重置 idle 时钟。** ⛔ **所以，长时间的构建期间机器人也不会睡着。**

⚠️ **表情有寿命。** `greeting` 和 `closing` 在三秒后回到 `present`。**这是产品决定，不是测量值。** **一直留到下一个事件的脸，会对那个瞬间持续了多久说谎。**

## 三十三个事件，三种类型

**三十三个名字，来自 hooks 文档的表，2026-10-18 读取。** ⛔ **名字不在这里发明。** 不在列表里的名字会抛出 `UnknownEvent`——**上游新增的事件会以错误出现，而不是被静默地当作默认值。**

⛔ **分法不是「反应／不反应」。它是同一个事件的三种接收方式。**

### 转换——六个，改变阶段

| 事件 | 阶段 | 为什么 |
|---|---|---|
| `SessionStart` | `greeting` | 会话开始了 |
| `UserPromptSubmit` | `working` | 人的回合结束，机器的回合开始 |
| `PermissionRequest` | `blocked` | **唯一的打断**——机器需要人 |
| `Stop` | `closing` | 回合结束了 |
| `StopFailure` | `closing` | 因为 API 错误，回合死了 |
| `SessionEnd` | `resting` | 会话正在离开 |

### 证据——十二个，读取但不表达

| 事件 | 为什么 |
|---|---|
| `PreToolUse`, `PostToolUse`, `PostToolBatch` | 回合还活着；身体不按工具调用逐次说话 |
| `PostToolUseFailure` | 数着；一个回合里的第三次，是最初的信号 |
| `PermissionDenied` | 等待结束了——拒绝也是一种结束 |
| `Notification` | 它唤醒机器人并重置 idle 时钟；⛔ **它不是人的回答** |
| `MessageDisplay` | 它没有开始；文字显示期间一直在响 |
| `SubagentStart`, `SubagentStop`, `TeammateIdle`, `TaskCreated`, `TaskCompleted` | 回合内部；外面的 `Stop` 才是信号 |

### 忽略——十五个，不读取，但仍是生命的证据

| 事件 | 为什么 |
|---|---|
| `Setup`, `InstructionsLoaded`, `ConfigChange`, `CwdChanged`, `DirectoryAdded`, `FileChanged`, `WorktreeCreate`, `WorktreeRemove` | 会话的上下文变了；身体没有参与这件事 |
| `UserPromptExpansion` | 它在 `UserPromptSubmit` 之后立即响起 |
| `PreCompact`, `PostCompact`, `PreModelSwitch`, `PostModelSwitch`, `Elicitation`, `ElicitationResult` | 还没有带数字的行为——⛔ **而且词不在数字之前加上** |

⚠️ **`ignored` 不是「没有送到」。** 三十三个全部都会重置 idle 时钟，并把机器人从 `resting` 唤醒。**「不表达」不是「没看见」。**

⚠️ **`no-behavior` 不是「没有行为」，而是「没有带数字的行为」。** 词汇是映射，不在表里的词就不在词汇里（`references/README.md`）。⇒ **对其中的任何一个作出反应，都会在它还变不成机体能做的事之前，先用掉一个词。**

## 四条通道

| 通道 | 声音 | 默认 | 运送什么 |
|---|---|---|---|
| 屏幕 | 无声 | 始终 | 脸——看过去时的信息 |
| **RGB LED ×12** | **无声** | **始终** | 呼吸、暖色、注意、熄灭——**周边视觉里的在场** |
| 脖子（2 轴） | 舵机声 | `--motion on` | **只在转换时** |
| 扬声器 | 有声 | `--sound off` | **在六个转换中的四个各带一个词**——`hello`、`pip`、`chime`、`fall`；播放它的是基板。⚠️ **即使开关打开，21:00–05:00 也会关闭它** |

⛔ **这里没有「无声模式」，因为名字会是假的。** 舵机会响。**运动和声音是两条轴，不是一个 enum**，脸和光不服从任何一条——**它们不发出声音。**

✅ **从 2026-10-19 起，扬声器除了开关还有时刻。** `projects/stackchan/quiet.py` 只回答一个问题——**这个时点是否在 21:00 与 05:00 之间**——而守护进程在每个事件读一次墙上时钟，把答案作为值往下传（`Room.offer(..., quiet=)`）。⛔ **核心仍然不读时钟。** ⚠️ **安静时间只关闭声音字段，别的什么都不关**——脸、光和脖子照旧。**沉默不等于不在。** ⚠️ **边界是整点，不携带分钟**：20:59 是白天，21:00 是安静，05:00 又是白天。✅ **而自 0.19.26 起，安装好的作业指名 `--sound on`**——作者要求了它——所以白天开口，夜晚不开口; ⛔ **作业不指名时刻**，因为时刻只住在 `quiet.py`。

✅ **光是意义，不是 RGB。** `Light` 是 `off`、`dim`、`breathe`、`warm`、`alert`、`error`。映射到十二个像素是固件的工作，**这一台的 LED 顺序和颜色顺序，这里的任何记录里都没有。** 原厂固件公开了 `set_led_color`；这一层不调用它。

## 密度——只在转换时

⚠️ **身势只在阶段转换时被选中，节奏由事件本身封顶：** 回合打开时一个 `look_up`，长回合关闭时一个 `nod`——**每个回合两个节奏身势。** `PermissionRequest` 是打断而不是节奏，不计入这个数。**但逃不过身体自己的下限。**

⛔ **离前一个身势不到一秒的身势会被丢弃，而不是排队**——身体栏变成 `cooldown`，`Companion.dropped` 会计数。两个理由：**排队会让这一层决定指令之间的间隔。** 并且**在 10/04 的那一台上，小于约一秒的间隔会让舵机停住并让电源轨掉落**（`MOVE_SETTLE = 1.0`）。⚠️ **那个 1.0 秒是这个包里唯一的借来的数字**——**它是另一台的下限，不是这一台的测量值。** **向安全侧借，标明是借的，在测量这一台的那天替换掉。**

✅ **光不等身体。** 即使舵机在 cooldown，阶段仍然改变，LED 也仍然改变：**唯一的打断可以失去脖子，但不会失去颜色。**

## 两个以上的窗口，一个房间

⚠️ **可能同时开着两个以上的 VSCode 窗口、跑着多个会话**（作者的要求，2026-10-18）。**脖子只有一根，脸只有一张**——无法同时映出全部，**也不能在它们之间来回转**：来回转时每一次身势都会撞上那一秒的下限，**脖子会在终端之间发抖。**

✅ **所以注意力只有一个，而且不容易离开**（`Focus`）——**最先开口的窗口取得它，并一直持有到沉默为止。** 持有者沉默 **90 秒**后——**同一个 `IDLE_SECONDS`，不是新的数**——注意力空出，由下一个开口的窗口取得。**所数的只有「持有者是不是只有一个」。**

✅ **注意力会移向人有所动作的窗口**——`SessionStart` 与 `UserPromptSubmit`——**以及机器需要人的瞬间**——`PermissionRequest`。⛔ **背景窗口的 `Stop` 不会移动它**: 机器结束，不等于人在看着那里。若允许移动，**背景任务每结束一次，脖子就会甩一次。**

⚠️ **其他窗口不会被丢弃。** 它们的事件会重置房间的 idle 时钟，并以理由 `distant` 报告——**「看见了、还活着、不是这一个」**。⛔ **那里的 `sent` 同样是 `False`。**

## 失败——连续三次

⚠️ **一次工具失败是日常，会被重试。** 它得到 `observed`，仅此而已。

- **同一个回合里连续三次 `PostToolUseFailure`**——中间没有成功的 `PostToolUse`——进入 `concern`：**光变成 `alert`，脸不变。** ⛔ **对测试失败发怒，不是这里的反应。**
- **`angry` 留给 `StopFailure`**——回合因 API 错误而死。那才是异常事件，也是唯一配得上这张脸的。
- **成功的 `PostToolUse` 把计数清零。**

## 运行它

从仓库根目录:

```
python3 -m projects.stackchan                                   # 把三十三个按三种类型打印出来
python3 -m projects.stackchan --event SessionStart@0 --event Stop@3
python3 -m projects.stackchan --motion off --event Stop@0.1
python3 -m projects.stackchan --sound on --event SessionStart@0
python3 -m projects.stackchan --json --event PostToolUseFailure@0
python3 -m projects.stackchan --event left:SessionStart@0 --event right:PermissionRequest@2
python3 -m projects.stackchan.daemon --socket /tmp/ekl.sock   # 监听；Ctrl-C 或 SIGTERM 停止
echo '{"session_id": "main", "hook_event_name": "SessionStart"}' | python3 -m projects.stackchan.hook --socket /tmp/ekl.sock
```

⚠️ **窗口写作 `窗口:事件@秒`；不写窗口就是 `main`，所以单窗口的剧本读起来与以前相同。** ⚠️ **时间由剧本给出，不从时钟读取。** 剧本不能倒流；倒流的剧本会被拒绝。这使一次运行可以复现——**也是 CLI 不是钩子所调用的东西的理由**（见下）。⚠️ **每一行都显示光和身体，脸改变时还显示脸的画**——**即使身势被丢弃，也仍然读得出反应。**

## 脖子，由引擎来动（0.19.10）

✅ **`projects/stackchan/neck/` 是本仓库里第一台写出姿态行的主机。** `motion.py` 是纯的：两个姿态与一个时长进去，`engine/trajectory` 的样本用电线自己的编码器编好后出来。`__main__.py` 是边缘：用绝对期限追每个样本自己的时刻，每个刻度用 `os.open`/`os.write`/`os.close` 写一行——和守护进程同一条路径。

```
python3 -m projects.stackchan.neck --dry-run --start 80 500 --end 350 500 --duration 1.3
python3 -m projects.stackchan.neck --port /dev/cu.usbmodem101 \
    --start 80 500 --end 350 500 --duration 1.3 --period 0.02 --hold 0.8
```

⛔ **两端在命令行上以十分之一度的整数被名指，这是有意的**：测得的姿态属于基板（`main/main.cpp`），而这个包依然不持有机器 2 的任何一个数。**姿态行运数，迁移帧不运数。** 这个模块写前者，守护进程写后者。

⚠️ **时长是约束，不是口味——但那个数字在 0.19.11 变了。** 在此之前，这一段说舵机以约 40°/s 跟随——那是 `speed=100`，**固件写下的减速，不是舵机的天花板。** **2026-10-18，与它自己的原厂调用（`time=20, speed=0`）相比测得：112 个计数（35°）在 200 ms 以内，约 175°/s。** ✅ **固件现在写原厂的调用，参照最快可以到舵机自身的界限，大约 `度 / 93`。** 下面的七个区段以约 `度 / 60`（峰 ≈112°/s）流出。⛔ **这里的任何测试都看不见它**——测试没有舵机。

✅ **同一天，在这台个体上测得：七个区段、822 个被应用、零拒绝、零 clamp**，一次 47° 的移动停在离目标一个计数的地方。✅ **而在固件的写法改变之后，同样的七个区段以三分之一的时长：228 个姿势、零迟到、板子上应用了 410 个（228＋保持 182）、零拒绝、零 clamp——作者的判定是「かなり良い。これでOKだと思う。」**（`projects/stackchan-firmware/records/2026-10-18-the-neck.md`）。被检验的是机构：`tests/test_stackchan_neck.py`，四十项测试。

### 接缝——自 0.19.14 起，一个事件让一切一起动

✅ **钩子的转换现在让脸、光和脖子一起动。** 守护进程**在自己的 `select` 循环里持有一个 `Stream`**——没有子进程，没有第二个时钟——从给帧盖上时间戳的同一个 `at` 出发，为同一个事件流出姿态行。⛔ **那个事件发出的帧运着 `gesture: null`**: 板子的 `PlayGesture` 会堵住主循环数秒，其间写下的姿态是延迟才被应用的——**一个事件不能让头动两次。** ⚠️ **日志行与给客户端的回信仍然名指这一层选中的身势**；消失的是电线上的那个栏位。

- **五个姿态是板子那张表的副本**（`neck/gestures.py`），副本由一项读 `main/main.cpp` 的检查守住：表一动，测试就变红。⛔ **正本的顺序没有变**——机器是正本，这是副本。
- **`nod` 是接在一条时间轴上的两段。** ⛔ **接缝上并排两个样本，头就会停一个刻度**，而那正是作者所说的「動きが硬い」的形状。
- ✅ **自 0.19.23 起，主机向板子询问头在哪里**——每个身势，它在将要用来流出的同一个 fd 上写一行 `bench pos`，并在同样的 `PORT_WAIT = 0.5` 之内读回。⚠️ **读到的姿态就是起点**——因此启动后的第一次转换，只要控制台回答，也会被流出。⛔ **只在身势的瞬间询问，绝不按时钟询问**: 定期的查询会切入正打在同一个控制台上的 `bench` 行——**控制台也是人的。**
- ⛔ **控制台不回答时，什么也不捏造。** 起点落回实际写下的最后一个姿态，再落回板子要演的表的终点姿态；两者都没有时，**第一次身势交给帧。**
- ⛔ **日志把两种失败分开。** `{"position": null, "heard": false}` 是沉默的控制台；`{"position": null, "heard": true}` 是回答了 `yaw=no answer` 的控制台——**舵机沉默了。**
- ✅ **2026-10-19 在机体上测量:** 查询被写下，板子回答了它（`{"position": null, "heard": true}`）。`bench pos` 打印 `yaw=no answer pitch=no answer`，`bench scan` 返回 **0 id(s)**。⇒ **路径被测量了；来自这台机体的位置还没有。** 舵机总线什么也没有回答，而 ⛔ **这里的代码无法补上它。**
- **此后的每一个动作都从实际写下的最后一个姿态开始**——不是上一个计划的终点。被打断的计划，停在离它瞄准的地方不同的位置。
- ⛔ **短的写入会停住流**，行变成 `sent: false`。下一个身势从写下的最后一个姿态重新开始。
- ⛔ **流为一个身势持有端口，而不是每个姿态开一次**（0.19.15）。帧仍然是 `os.open`/`os.write`/`os.close` 各一次，帧与帧之间什么都不持有; **流只开一次端口，每个姿态在 `PORT_WAIT = 0.5` 的上限下写出，在要结时关上。** ⚠️ **第一种形式被测出会让守护进程卡死**: 在 50 Hz 下反复 open/write/close，会在第四次或第五次时卡在 `open()` 里，信号够不着那里。**什么也接收不了的端口会让流结束，打不开的端口会把身势留在帧里交给板子。**

⚠️ **机构在机体上被测过一次，然后眼睛来了。** 2026-10-19，给控制台挂上读取方，把流实况重放了一遍。板子印出 `pose: stream started — goals on the present positions (yaw 504, pitch 780), torque on`，然后在沉默之后印出 `pose: stream lost after 500 ms — torque released` 和 `pose: 23 applied, 0 refused, 0 clamped`; 那个身势在守护进程那里的要结是 `{"neck": "look_side", "applied": 23, "late": 19, "held": 29}`。⛔ **二十三个里有十九个是延迟才应用的**——板子的主循环还抱着上一个身势。✅ **同一天稍晚，在已安装的守护进程运行中，作者说「さっき首が動いていたよ」**——脖子从一个钩子事件动了。**记录是 `projects/stackchan-firmware/records/2026-10-19-the-join.md`**，而⛔ **同一几分钟里流出的两个身势，眼睛抓到的是哪一个，它不确定。**

## 钩子还缺什么

⛔ **Claude Code 的钩子是一个事件一个进程。`Companion` 是一个在事件之间保持阶段、期限和 cooldown 的对象。** 这里没有任何东西把那个状态跨进程携带。

⇒ **一个长命进程现在有了**——`projects/stackchan/daemon/`，它拥有时钟、companion 和套接字。**核心（`room.py`）不读时钟、不读套接字，边缘（`__main__.py`）独自持有这两者。** ✅ **它被安装了**：launchd 用户代理在登录时启动它，而全部三十三个钩子事件都经由客户端到达它。 ⚠️ **直接接到这个 CLI 的钩子，会在每个事件上重置阶段和 idle 时钟**——正是它要防止的洪水，而且更糟：**机器人永远无法安定，也无法入睡。**

✅ **而同一天，客户端也有了**——`projects/stackchan/hook/` 从标准输入读一个事件，发送一行，**什么都不打印，无论发生什么都以 0 退出。** ✅ **它在 `settings.json` 里注册于全部三十三个事件。**

✅ **客户端发送的是事件的名字和窗口的名字，而不是提示词。** 时间由守护进程在行到达时盖戳，所以客户端不带时钟，也不带状态。机器人需要知道回合开始了，而不是说了什么；**需要窗口的名字，只是因为窗口共享一个身体。** **用结构守住隐私，而不是用方针。** ⚠️ **启动与停止的设计是 `docs/stackchan-daemon.md`**——**循环、套接字、客户端、launchd 任务和 `settings.json` 里的注册，都已经建好，并安装在这台主机上。**

✅ **通往机体的路已经不再缺任何一块:** LED 有了驱动，屏幕自 0.19.12 起有了渲染器，扬声器自 0.19.13 起有了声音，传输路径也已选定——全都在这个包之下，在 `projects/stackchan-firmware/` 里。**这一层的输出是 `Decision`；消费者是终端、守护进程，以及经由守护进程、每帧一行到达的板子。**

✅ **自 2026-10-18 起，它将要被发送的那个帧作为源码存在**——`engine/backend/protocol_stackchan.py` 编码并解码一行 ASCII，`schemas/stackchan-command.schema.json` 是两端共读的契约。✅ **传输路径已选定并连上**——`--port`，每帧一行，安装的 plist 点名了端口。✅ **而板子会执行身势的词**：`projects/stackchan-firmware/` 承载着在这台个体上测得的五个姿态（`projects/stackchan-firmware/records/2026-10-18-the-gestures.md`）。✅ **自 0.19.13 起，第四个栏位也携带一个词**——`sound`，来自四词的闭集——板子把它变成音（`records/2026-10-18-the-voice-zh.md`）。⛔ **这条电线仍然不承载来自这一层的任何数字**——出去的是词，机体把词变成计数。

## 保住房间的进程（2026-10-18）

✅ **`projects/stackchan/daemon/` 是唯一的长命进程。** `room.py` 是核心——请求的形状、房间、下一个期限——它不读时钟、不读套接字、不读环境。`__main__.py` 是边缘，它是唯一打开套接字并读取 `time.monotonic()` 的文件。

- **套接字就是锁。** 第二个实例探测它，不对机体说一个字就以退出码 3 结束；陈旧的套接字会被 unlink 并替换。没有 pidfile。
- **一行 JSON 进，一行 JSON 出**——`{"session": …, "event": …}`。**未知的键会被拒绝**，所以提示词无法搭车；未知事件和读不出的行会带着代码被拒绝。
- **时间由守护进程盖戳。** 客户端不发送时钟。
- **循环等待套接字或下一个期限**——`min(hold_until, idle_until, quiet_until)`——醒来时发出 `settled` 或 `slept`。**没有固定的刻。**
- **`SIGTERM` 让它停止**，unlink 套接字并以 0 退出。⛔ **什么也不发送，不是一条停止命令**：一帧就是一次 `os.open`/`os.write`/`os.close`，而让板子松开扭矩的不是这里的一个词，是 500 ms 的沉默。

**客户端**是 `projects/stackchan/hook/`——一个事件一个进程。它读标准输入（上限 1 MiB），**只重建两个栏位**，发送，**不读回信就关闭。** **守护进程不在，不是钩子的失败: 以 0 退出，保持沉默。** 重建在 `client.line_from` 里，是纯函数，不用进程就能检查。

✅ **2026-10-18 安装完成。** 任务是 `launchd/embodied-kinetic-loom.stackchan.plist`——`~/Library/LaunchAgents/` 里那一份的副本——而客户端注册在全部三十三个事件上。**记录、实测的行为和卸载路径都在 `docs/stackchan-daemon.md`。**

## 离开房间的东西

✅ **`projects/stackchan/outbound.py` 把 `Decision` 变成 `Frame`**——脸（或 `null`）、光、身势（或 `null`），以及声音（或 `null`）。**它是纯的，不持有时钟，也不点名任何一台机器。**

- **帧在机体该显示的东西发生变化时发出**——脸或光——**或者选中了身势，或者点名了声音，或者它是这个进程的第一个决定。** ⛔ **声音是事件而不是状态**: 光被记住并重新发送，声音不被记住；那个栏位里的 `null` 意味着*这一帧沉默*。 ⛔ **第一个决定一定发出，因为在那之前的机体状态是未知的**; 决定没有点名的脸，由帧自身的状态补上，所以机体不必记住自己曾映着什么。
- ⛔ **事件的理由并不划分状态变化。** `blocked` 中的 `PostToolUse` 以理由 `OBSERVED` 把阶段带回 `working`，光却可能不动; 担忧改变光，不改变阶段。**若按事件种类去数帧，就会发出不携带变化的帧，并漏掉不携带转换的变化。** 所以规则读的是状态，不是理由。
- ⚠️ **这不是流。** 一个阶段里的一百个证据事件，只生出一个帧。
- **守护进程把帧写成一行**——`{"frame": "<一行 ASCII>", "sent": false, "at": …, "session": …}`——而那一行由电线测试所守的同一个编码器产出，**所以日志不会偏离契约。**
- ✅ **任务点了端口时就会发送**——同一行被写进端口，而 `sent` 说的是主机的 tty 是否收下了它。⛔ **`sent: true` 说的是主机的 tty，不是板子收到了它**：送达只被证明过一次，**靠板子自己的控制台把帧打印出来**。✅ **屏幕在对面自 0.19.12 起有了渲染器**——板子从帧里的词画出原厂的脸——而 ⛔ **仍然为真的一点是: 这一层从不画它。** ✅ **2026-10-18，已安装的守护进程在一次真实钩子事件上写下了第一个帧行**——而 ⛔ **观测到的是一行，不是运动。**

## 检查了什么

**`tests/test_stackchan_behaviors.py` 有三十五条主张，`tests/test_stackchan_daemon.py` 有三十六条，`tests/test_stackchan_hook_client.py` 有二十一条，`tests/test_stackchan_wire.py` 有二十八条，`tests/test_stackchan_outbound.py` 有十三条，`tests/test_stackchan_neck.py` 有四十条，`tests/test_stackchan_readback.py` 有十条**，它们与其余检查一起运行:

- 列表是三十三个，没有重复；每个事件恰好属于三种类型之一，三种类型分割整个列表。
- 每个事件都带理由代码——**没有空白。**
- 一个剧本到达全部六个阶段、五张脸和六种光。
- 长回合点头，短回合不点头。
- 连续三次失败是第一个信号，第四次不是，成功会重置计数。
- 到达 `angry` 的路只有 `StopFailure`。
- `PermissionRequest` 是唯一的打断，`Notification` 不会结束等待。
- **三十三个事件全部会把机器人从 `resting` 唤醒**——包括被忽略的那些。
- 证据事件会重置 idle 计时器。
- 表情到期并回到 `present`。
- cooldown 里的身势被丢弃，**但光仍然改变。**
- 关掉运动，脸和光仍然保留。
- 声音默认不出，并在六个转换中的四个各带一个词——其余两个沉默。
- **即使开关打开，21:00–05:00 也关闭声音字段**，对脸、光和脖子不做任何事。
- 层能选择的每一个声音词，都是电线的闭集所点名的。
- **一个身势也不会被发送**——每一行的 `sent` 都是 `False`。
- **有多个窗口时，最先开口的窗口取得注意力**；人在另一个窗口动作时它会移过去，工具调用与背景窗口的 `Stop` 不会，背景窗口的 `PermissionRequest` 会夺走它。
- **规则数不到二**: 三个窗口也按同一条规则行动。
- 注意力在持有者沉默时、结束时空出；在那之前，持有者的事件让房间保持醒着。
- 剧本可以给窗口命名，每一行都说出它来自哪个窗口。
- 理由和身体两栏都是闭集，而且都能到达。
- 剧本可复现，倒流的剧本被拒绝。
- parser 在三种语言里都能建起，而且帮助不同。
- **这个包里没有机器 1 的名字、数字或模块**——用 AST 走过 `DofRealityWire`、`Envelope`、数字 190、512、833，以及任何来自 `engine` 的 import——并且没有 `motions/` 目录。

**守护进程再加三十五条:**

- 套接字会回答，而日志里的行就是客户端收到的同一行。
- 第二个实例以 3 退出，第一个继续回答。
- 陈旧的套接字会被 unlink 并替换。
- 未知的键、未知的事件、读不出的行，各自以自己的代码被拒绝。
- **提示词到不了日志**——秘密不在守护进程打印的任何一行里。
- 什么都不发的客户端会被关闭，下一个请求仍然能通过。
- 干净的退出会删除套接字。
- 下一次醒来先是表情，然后是 idle 时钟；`blocked` 和 `resting` 没有期限;
- **问候写下一个帧行，其中的 `sent` 是 `False`**——那一行会被解码回 `Command(face="greeting", light="warm", gesture="look_up")`;
- **不变的事件不写下第二个帧。**
- **第二次转换从第一次结束的姿态之后流出姿态行，而帧先运 `look_up` 再运 `null`**——写出的每一行姿态都能解码，日志里的 `neck` 行名指 `look_side` 与至少五个姿态。
- **不回答的控制台，被写入而不被相信**——查询到达端口，`heard` 是 `False`，第一次身势交给帧；
- **给出位置的控制台，从那里流出**——第一次转换也是，而行记录测到的姿态；
- **不给出位置而回答，仍是回答**——行说 `heard: true` 和 `position: null`。这与沉默不同；
- **一次流只开一次端口**，不是每个姿态开一次。
- **什么也接收不了的端口会让流结束**，而不是等待，行变成 `sent: false`。
- **打不开的端口把身势留在帧里**，交给板子去演。

**客户端再加二十一条:**

- 一份完整的钩子输入只产出一行 `session` 与 `event`——**提示词、cwd 和工具输入都不在其中。**
- 缺少两个栏位的输入被丢弃，未知事件在到达套接字之前被丢弃。
- 那一行能用守护进程自己的模式读出，并且不超过守护进程的上限。
- **套接字路径只有一种拼写**，两个入口都用它。
- 真实的输入到达房间，而其中的提示词不在守护进程的日志里。
- 没有守护进程、读不出的输入、过长的输入，都是沉默地以 0 退出。
- **客户端不等待回信**——永不作答的对方也不会让它迟延。
- **一个守护进程在两个不同进程之间保住阶段**: 第一个进程的 `SessionStart` 与第二个的 `Stop` 读作 `greeting` 与 `closing`，**而两个进程都没有持有任何状态。**
- **两个窗口经过两个客户端，注视仍然只有一个**，背景的 `Stop` 被报告为 `distant`，阶段不变。

**电线再加二十八条**——帧、它的契约，以及它的机体那一端:

- 1,080 个帧往返——**其中 125 个不带任何 `null`**——而没有哪一个携带数字;
- 帧是一行 ASCII，而 `null` 的栏位是以值在场，不是缺失;
- 未知的键被拒绝（`prompt` 无法搭车），未知的词按栏位被拒绝，而 `light` 必须存在且永不为 `null`;
- **`sound` 必须存在，可为 `null`，其值是四个词**——`null` 是*这一帧沉默*，不是*保持上一个*;
- 编码器恰好拒绝解码器所拒绝的;
- 契约、编码器与固件的字面量拼出同样的词，**而固件里没有哪一台机器的角度**;
- 电线只导入 `json` 与 `dataclasses`，**不从机器 1 的 `protocol` 导入任何东西**;
- 模拟器记录本该被发送的东西，什么也不回答。

**外发的帧再加十三条**——在还没有电线的当下，房间决定摆到机体面前的东西:

- 第一个决定一定发出，并补上它没有点名的脸;
- 什么都不改变的决定不发出帧——**一百个证据事件只生出一个**;
- 只有光变化时，发出 `face: null` 的帧; 只有身势时也发出帧;
- **只有声音也发出帧，而且这个帧不会被重复**——`Outbound` 记住光，却不记住声音;
- 每个转换带自己的词，其中两个沉默;
- 每一个发出的帧都能按契约读出，并在编码器上往返;
- **帧的任何一个栏位都不是数字。**

⚠️ **这些主张中没有一条是关于机体的。** 一次绿色的运行说的是，**这一层按它被告知的方式计算了**——与 `CLAUDE.md` 对五项检查要求的同一句话。

## 这里没有的东西
