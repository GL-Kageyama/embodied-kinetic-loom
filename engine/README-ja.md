# engine/

**決定論的な核心**——**補間・イージング・平滑化・制限。** この4つは関数であり、**ゆえにこの工房が厳密に検査できる4つである。**

## ここに在るもの

```
intent.py           Motion Intent の読み込みと、schemas/ に対する検証
trajectory/
  profile.py        機体の族——端の速度がゼロの曲線
  easing.py         表現の族——CSS の cubic-bezier。⛔ 機体へは通さない
  smooth.py         端を動かさない平滑化
  limits.py         軸ごとの上限と、合成の上限
  plan.py           軌道と、その標本
  admit.py          通すか弾くか——計画時の側だけ
backend/
  protocol.py       5バイトのフレーム。⛔ 機体1のものである——3つの危険と、意図的に書かない1つ
  wire.py           ⛔ 継ぎ目——機体の数え方と、それがバイト列になる手順
  cycle.py          周期ループ——締切は絶対時刻、時計は渡される
  gate.py           実際に出て行くものを見る門。⛔ 拒否は沈黙ではない
  axis_map.py       自由度→モーター。⛔ 既定値なし——対応に正準は無い
  transmit.py       壁時計で軌道を引く——次の標本ではなく、いちばん近い標本
  mock.py           箱のふりをするもの。⚠️ プロトコルの試験であって、安全の試験ではない
```

## なぜ2つの族が、2つのモジュールに住んでいるか

**画面と機体は、曲線に逆のものを求めるからである。**

`Back`・`Elastic`・`Bounce` は、前へ動く前に後ろへ加速する。**画面では「ため」に見える。機体では、逆向きの加速度である。** ゆえに表現の族は `easing.py` に残り、**機体の族——`min-jerk`、`trapezoid`、そして 0.19.11 からの `spring`——だけが `plan` へ渡れる。**

⚠️ **`Spring(sharpness)` は、純正の Stack-chan ファームウェアが首を動かしていた形である**: 臨界減衰のばねで、速度の山は `u = 1/a` に来る——min-jerk の `u = 0.5` とは違い、前寄りである。⛔ **生のばねは `u = 1` でも速度を持つ**ので、族の規則——両端で速度ゼロ——は補正の1項で守られ、その代価は端の加速度がゼロでないことである（台形が落ちるのと同じ検査に、ばねも落ちる）。**`sharpness` の既定は 5.0 であり、呼ぶ側の数であって、測った数ではない。**

⛔ **一方の族から他方への写像は、存在しない。そしてこのエンジンは、それを作らない。** 設計ノートはその写像について、**自ら「提案であって設計ではない」と書いている。** ここに書けば、このリポジトリの発明になる。⇒ `easing.MAPPING_TO_MACHINE` は `None` のままで、**それが今も `None` であることを検査が1本見ている**——**誰かが書いた日、その変更が意図的で目に見えるように。**

## 何がこれを決定論的にしているか

**同じ入力なら、同じビット列が出る。そしてその主張は、2つのやり方で守られている。**

- **`tests/test_purity.py` は `engine/` の全ファイルの import を読み、`random`・`time`・`os`・`socket`・LLM のクライアントのどれかがあれば落ちる。** **2回走らせて比べるだけでは足りない**——**その2回が、たまたま一致しただけかもしれない。** **見るべきは import である。**
- **標本の時刻は、足し上げずに数え上げる**——`duration * k / (count - 1)` であって、`t += step` ではない。
- **`easing.py` の二分法は、回数が固定である。** 収束判定にすれば、結果が入力の関数であるのは名前だけになる。

⚠️ **軌道の端は、厳密に置かれる。** 最初の標本は与えられた始点そのもの、最後は終点そのものである——**浮動小数では `start + (end - start)` が `end` にならないことがあり、** **最後の1単位だけ目標に届かない指令は、届かなかった指令である。**

## 2つの門と、決まっていない席

⚠️ **この節の機体に固有の事実は、すべて機体1のものである**——DOF Reality の制御箱。**門そのものは、機体を1つも名指さない**: `backend/gate.py` は `Wire` と数の組を受け取るだけで、**自分がどちらの機体を守っているかを知らない。**

**`admit.py` は判定であって、配置ではない。** **Safety が層なのか関門なのかは未決であり、どちらでもこの関数は呼ばれる**——**ファイル名を `safety.py` にしていないのはそのためである。** そう名乗れば、まだ開いている問いを閉じたことになる。

⛔ **そして、これは計画時の側だけである。** 軌道を制限に対して検査するが、**時計については何も知らない。** **`backend/gate.py` がもう一方の側である**——**出て行く1フレームを見る。ただし経過時間は、仮定せずに実測する。**

**実行時の門にしか見えないもの、そしてその理由:**

| 何 | なぜ計画時に見えないか |
|---|---|
| **隣り合う2フレームの段差** | ⛔ **機体1の上流ファームにソフトスタートもソフトストップも無い。** ある指令が段差になるかは、**それを送る間隔で決まる**——そして計画は時計を持たない |
| **送る時刻そのもの** | 計画は `t` の関数である。`now` を知らない |
| **自由度がどのモーターへ行くか** | ⛔ 正準の対応が無いので、**門はそれを決めない**——呼ぶ側が渡す |

⛔ **そして門のいちばん重い決定は、「拒否の形」である。門は、何も返さないことをしない。**

> **送信をやめると、15秒でトルクがおよそ 1/4 になる——そして、モーターは止まらない。**

⇒ **ゆえに拒否は、最後に通した組を返し、それを送り続ける。** **この機体で「止まっている」にいちばん近いのは、それである。** ⚠️ **そして、それは「止める」でもない**——**プロトコルに停止コマンドが無い。** **門はそれを直せない。できるのは、悪い1フレームを出さないことだけである。**

⛔ **だが、保つだけでは軸が凍る。そしてそれは、試験を書いている最中に見つかった。** 門の基準は*最後に通した値*、送信が提案するのは*壁時計の値*——**提案は先へ進み続けるので、開きは縮まらない。** ⚠️ **そして弾くたびに門の時計が進むので、溜まった時間が毎回捨てられた。** **1回弾かれると、軸は二度と動かなかった。**

⇒ **ゆえに弾かれた軸は、門自身が許す速さで目標へ寄る**——`velocity × elapsed`、**つまり門がもともと通す大きさである。** ⛔ **安全の議論に新しい仮定は1つも入らない。門が「段差だ」と言ういちばん大きい大きさが、そのまま門が取るいちばん大きい大きさになる。** ⚠️ **枠の外の目標は、寄らずに保つ**——**枠の外は、寄る先ではない。**

⚠️ **門は組ごとに判定する。** 1モーターずつ通せば、**誰も計画していない組み合わせ**が機体の上に現れる。

## 時計は import されない

**`engine/` は `time` を import してはならない**——**時計を読む軌道は、関数ではないからである**（純粋性の検査が押さえている）。**ゆえに周期ループは、`now()` と `sleep()` を呼ぶ側から受け取る。**

⚠️ **これは純粋性のための方便だけではない。** **周期を検査可能にするのは、これである**——**時計を渡せば、設計ノートが「締切方式で書かれている」と「`sleep(period)` を毎回呼んでいない」という*形*としてしか書けなかった2つが、実行時の主張になる。** `grep` は、その行がソースに在ることは見える。**走ったときにその行が成り立つことは見えない。**

⛔ **そして `period` に既定値は無い。** ノートは、**同じ機械が 5 ms と 10 ms の二状態を取る**ことを実測している。**片方を既定値にすれば、実測を定数に変えたことになる。**

## 継ぎ目——その数は誰のものか

**`backend/wire.py` が、機体の数え方を知っている唯一の場所である。** メソッドは3つ、それ以上は無い:

| メソッド | すること | ⛔ いつ |
|---|---|---|
| `axis_count()` | この機体が持つ軸の数 | 組み立て時——**電線が表せない軸へ、門は指令を出せない** |
| `quantize(value)` | この機体の数え方に丸める。表せなければ投げる | ⛔ **門の手前**（下を見よ） |
| `encode(commands)` | 丸めた組をバイト列にする | ⛔ **門の後ろ** |

- **`Command(axis, value)` が、門の話す通貨である**——モーター番号と、*その機体の*数え方での値。⛔ **`axis` は自由度ではない。** 名前（`pitch`／`roll`／`yaw`）は `axis_map.py` のものであり、**電線は名前を1つも見ない**——機体2には、名指せる3軸が無いからである。
- ⛔ **`envelope()` は、意図的に `Wire` に載せていない。** 枠は測定から導かれた政策であって、符号化の性質ではない——**運用者は、電線に触れずに枠を狭められなければならない。**
- ⛔ **`decode` も載せていない。** 機体1の読み側は2つの出典で食い違っており、意図的に書かれていない——**誰も実装できないメソッドを必須にするのは、型の付いた嘘である。**
- ⛔ **順序が効く。逆順は欠陥である。** `Transmitter.frames_at` は **`gate.submit` の前に**丸める——ゆえに表せない値は、**門が時計と前回値を進める前に**投げる。そして**後ろで**、`verdict.commands` から符号化する——**提案ではなく、門が通した組である。**

⛔ **そして、既定値だった数は、いま名前である。** 2026-10-15 まで、`Envelope` は `target_min = 190.0` / `target_max = 833.0` を既定として持ち、**`Gate`・`admit`・Pet の rig がそれぞれその既定を配っていた**——**4箇所が、どれも黙って「機体1」を意味していた。** **既定値は、それが誰の数かを言えない。** 測定値はいま、`backend.protocol.DOF_REALITY_ENVELOPE` に1回だけ現れ、**名前で**渡される。`Envelope` は数を1つも持たず、`Envelope()` はもう組めない。**数を書いた枠が他所で組まれていれば、`tests/test_limits.py` が `engine/` を歩いて赤くなる。**

⚠️ **機体はまだ1台である。** `DofRealityWire` はこのリポジトリ唯一の電線であり、**「電線は差し替えられる」は設計の主張であって、まだ実測ではない。**

## ここに無いもの

⚠️ **この節が並べるのは `engine/` に無いものであり、その項目は同じ理由を持っていない。** **不在と配置は、一覧の上では同じに見える——そして同じものではない。** **Pet の画面は、決定論的な核の中に住むように作られてはいない。**

| 何が | どこに | なぜ |
|---|---|---|
| **シリアル層** | まだ、どこにも | ⛔ **機体が握っている**——機体1の制御箱には2世代あり、プロトコルが2つある |
| **音** | どこにも | このエンジンは運動を駆る。**ここには音を出すものも、音を喰うものも無い** |
| **Pet の画面** | `projects/pet/`、0.4.0 で来た | ⚠️ **設計上、ここには無い。** 顔と身体は時計を共有する（`motion.py`）——**そして時計の共有は、顔を核の中へ入れる理由にはならない** |
| **語→値の写像** | `references/README.md`、0.6.0 で来た | ⚠️ **設計上、ここには無い。** D-02 の答えは読む者が読む表である。**核が読むのは型であって、語彙ではない** |

⛔ **そして1つの項目が、誰にも気づかれずにこの一覧を出て行った。** **「実行時の監視」と書いてあり、その行を編集した版で既に古くなっていた**——**`backend/gate.py` は上の「ここに在るもの」に、0.3.0 から載っている。** **それが実行時の門であり、その日に来た。** **このファイルは8つの版のあいだ、両方を同時に言っていた。**

⚠️ **それでも真なのは、もっと狭い主張である——ここには、返ってくるものを見る者が居ない。** 契約は開ループである——**門が見るのは、出て行くものだけである。** `decode_frames` は在り、`decode_feedback` は意図的に書かれていない——**箱の返事の形が、確かめられていないからである。**

**Mock と実機が最も食い違うのがシリアル層である**——⛔ **`flush()` が macOS の pty で無限にブロックすることが実測されている。** **Mock はシリアル層の上に座るので、Mock が緑でも、その1本については何も言わない。**

## フォールバックが支払う1つ

**`trapezoid` は、5つの検査のうち2つに、構造上落ちる——両端で加速度がゼロでなく、角でジャークが定義されない。**

**それはコードの欠陥ではない。台形プロファイルとはそういうものである。** **だが、それは「フォールバックを選ぶことが、検査を1つ外すこと」を意味する**——**ゆえにこのリポジトリは、それを発見に任せず、テストに書く。** **ジャークの上限を置けば、`admit` は台形を1つも通さない。置かなければ通る。**
