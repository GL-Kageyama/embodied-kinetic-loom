# engine/

**決定論的な核心**——**補間・イージング・平滑化・制限。** この4つは関数であり、**ゆえにこの工房が厳密に検査できる4つである。**

## ここに在るもの

```
intent.py           Motion Intent の読み込みと、schemas/ に対する検証
trajectory/
  profile.py        機体の族——端の速度がゼロの曲線
  easing.py         表現の族——CSS の cubic-bezier。⛔ 機体へは通さない
  smooth.py         端を動かさない平滑化
  limits.py         軸ごとの上限と、合成の上限
  plan.py           軌道と、その標本
  admit.py          通すか弾くか——計画時の側だけ
```

## なぜ2つの族が、2つのモジュールに住んでいるか

**画面と機体は、曲線に逆のものを求めるからである。**

`Back`・`Elastic`・`Bounce` は、前へ動く前に後ろへ加速する。**画面では「ため」に見える。機体では、逆向きの加速度である。** ゆえに表現の族は `easing.py` に残り、**機体の族——`min-jerk` と `trapezoid`——だけが `plan` へ渡れる。**

⛔ **一方の族から他方への写像は、存在しない。そしてこのエンジンは、それを作らない。** 設計ノートはその写像について、**自ら「提案であって設計ではない」と書いている。** ここに書けば、このリポジトリの発明になる。⇒ `easing.MAPPING_TO_MACHINE` は `None` のままで、**それが今も `None` であることを検査が1本見ている**——**誰かが書いた日、その変更が意図的で目に見えるように。**

## 何がこれを決定論的にしているか

**同じ入力なら、同じビット列が出る。そしてその主張は、2つのやり方で守られている。**

- **`tests/test_purity.py` は `engine/` の全ファイルの import を読み、`random`・`time`・`os`・`socket`・LLM のクライアントのどれかがあれば落ちる。** **2回走らせて比べるだけでは足りない**——**その2回が、たまたま一致しただけかもしれない。** **見るべきは import である。**
- **標本の時刻は、足し上げずに数え上げる**——`duration * k / (count - 1)` であって、`t += step` ではない。
- **`easing.py` の二分法は、回数が固定である。** 収束判定にすれば、結果が入力の関数であるのは名前だけになる。

⚠️ **軌道の端は、厳密に置かれる。** 最初の標本は与えられた始点そのもの、最後は終点そのものである——**浮動小数では `start + (end - start)` が `end` にならないことがあり、** **最後の1単位だけ目標に届かない指令は、届かなかった指令である。**

## 関門と、決まっていない席

**`admit.py` は判定であって、配置ではない。** **Safety が層なのか関門なのかは未決であり、どちらでもこの関数は呼ばれる**——**ファイル名を `safety.py` にしていないのはそのためである。** そう名乗れば、まだ開いている問いを閉じたことになる。

⛔ **そして、これは計画時の側だけである。** **設計ノートは、計画時の保証だけでは足りないと明言している。** **実行時の門はまだ無い**——実機とバックエンドが要る。

## フォールバックが支払う1つ

**`trapezoid` は、5つの検査のうち2つに、構造上落ちる——両端で加速度がゼロでなく、角でジャークが定義されない。**

**それはコードの欠陥ではない。台形プロファイルとはそういうものである。** **だが、それは「フォールバックを選ぶことが、検査を1つ外すこと」を意味する**——**ゆえにこのリポジトリは、それを発見に任せず、テストに書く。** **ジャークの上限を置けば、`admit` は台形を1つも通さない。置かなければ通る。**

## ここに無いもの

**バックエンド・Mock・Pet の画面・音。** どれも機体の応答を要するものであり、**ここにあるものは、物理的な機械を1度も動かしていない。** **語→値写像も無い**——**型の `quality` 欄を埋めるはずの語彙が、止まっている。** **実行時の監視も無い。**
